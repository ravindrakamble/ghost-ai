Source spec: `context/feature-specs/27-spec-generation-flow.md`

## Analyst Brief

### Scope statement

Build the backend-only plumbing for AI-powered spec generation: a `POST /api/ai/spec` route that authenticates the caller, resolves project access from a client-supplied `roomId` (never a client-supplied `projectId`), triggers a new `generate-spec` Trigger.dev task, and records a `TaskRun`; a `POST /api/ai/spec/token` route that issues a run-scoped Trigger.dev public token to the run's owner; and a `trigger/generate-spec.ts` task that validates its input with Zod, calls Gemini via `@ai-sdk/google` to turn the current chat history + canvas graph into a Markdown technical spec, and returns that Markdown as its task output. No frontend wiring, no spec editor UI, and no persistence of the generated spec happen in this unit — this is the design-agent-API/-logic pattern (specs 22/23) applied to spec generation, structurally parallel but not bundled with it.

### Concrete deliverables

- `package.json`/`package-lock.json` — **no new dependency expected.** `@trigger.dev/sdk` (spec 22), `@ai-sdk/google`/`ai` (spec 23), and `zod` (spec 25) are all already real, installed production dependencies. Confirmed by reading `package.json` directly. This is the first spec in the design/spec-generation chain that shouldn't need to touch this file at all — see Dependencies below.
- `lib/generate-spec-ai.ts` (new) — Gemini interpretation module, mirroring `lib/design-agent-ai.ts`'s lazy-provider-instantiation pattern (`GEMINI_MODEL_ID`, a `globalThis`-cached `createGoogleGenerativeAI` provider, `requireGeminiApiKey`). Unlike `design-agent-ai.ts` (which uses `generateObject` + `jsonSchema()` to produce a bounded action list), this module should use the `ai` package's `generateText` (or `streamText`) — the raw spec text's own "keep the task output as plain Markdown" instruction names free-form text output, not a structured schema. See Open Questions #4.
- `trigger/generate-spec.ts` (new) — mirrors `trigger/design-agent.ts`'s shape: exports `GENERATE_SPEC_TASK_ID`, a `GenerateSpecPayload` interface (`projectId`, `roomId`, `chatHistory`, `nodes`, `edges`), a `runGenerateSpec(payload)` function exported separately from the `task(...)` registration (same "unit-testable without Trigger.dev's runtime" reasoning spec 22/23 already established), and `generateSpecTask = task({ id: GENERATE_SPEC_TASK_ID, run: runGenerateSpec })`. Validates its payload with a real Zod schema (`z.object(...)`) before calling Gemini — the raw spec text's own explicit "validates input with Zod" instruction, unlike spec 22/23's manual-type-guard precedent for the design-agent task. Follows `trigger/design-agent.ts`'s existing try/catch/`logger.error`/rethrow convention for error handling.

- `app/api/ai/spec/route.ts` (new) — `POST`: auth (`getCallerIdentity`) → parse/validate body with Zod (`{ roomId, chatHistory, nodes, edges }` — **no `projectId` field accepted from the client**, per the raw spec text's explicit "Do not trust a client-supplied `projectId`" instruction) → `getProjectAccess(roomId)` (owner-or-collaborator, same gate as `/api/ai/design`) → `triggerGenerateSpec({ projectId: roomId, roomId, chatHistory, nodes, edges })` (the task's own `projectId` field is populated from the already-access-checked `roomId`, never from anything the client separately claims) → `prisma.taskRun.create` (reusing the existing `TaskRun` model — see Open Questions #6) → returns `{ runId }`.

- No `prisma/schema.prisma` change expected — see Open Questions #6.

### Acceptance criteria

1. `POST /api/ai/spec` accepts `{ roomId, chatHistory, nodes, edges }` in the request body. No `projectId` field is read from or trusted in the request body anywhere in this diff — project access and the task's own `projectId` value are both derived from the already-authenticated, already-access-checked `roomId` only.
2. `POST /api/ai/spec` returns 401 for an unauthenticated caller, and 404/403 (via `getProjectAccess(roomId)`) for a missing or non-member project, before any Trigger.dev call or Prisma write happens.
3. `POST /api/ai/spec`, given a valid authenticated owner-or-collaborator request, triggers the `generate-spec` task through the Trigger.dev SDK, creates one `TaskRun` row (`runId`, `projectId` = the validated `roomId`, `userId`, `createdAt`), and returns `{ runId }`.
4. `POST /api/ai/spec/token` returns 401 for an unauthenticated caller, and does not return a usable token for a `runId` that does not exist or does not belong to the caller (`TaskRun.userId` check, matching `/api/ai/design/token`'s precedent).
5. `POST /api/ai/spec/token`, given a `runId` owned by the caller, issues a Trigger.dev public token scoped to that run only, with a 1-hour expiration, and returns it to the client.
6. `trigger/generate-spec.ts` exports a `generate-spec` task accepting `{ projectId, roomId, chatHistory, nodes, edges }`, validates that payload with a real Zod schema before calling Gemini (rejecting malformed input, e.g. non-array `nodes`/`edges` or a wrong-shaped `chatHistory` entry, without ever reaching the AI call), calls Gemini via `@ai-sdk/google` to generate Markdown content from the chat/canvas context, and returns the generated Markdown as its task output.
7. No frontend/`components/*` file is changed anywhere in this diff.
8. No spec content is persisted anywhere (no Prisma write beyond the `TaskRun` row, no Vercel Blob upload, no filesystem write) — the task's Markdown output is returned only, never stored.
9. No new AI provider abstraction is introduced — `lib/generate-spec-ai.ts` reuses the exact same `@ai-sdk/google`/Gemini lazy-instantiation pattern `lib/design-agent-ai.ts` already established (same `GEMINI_MODEL_ID`/`globalThis`-cached-provider convention).
10. `types/canvas.ts` (`CanvasNode`/`CanvasEdge`/`CanvasNodeData`/`CanvasEdgeData`) and `types/tasks.ts` (`AiChatMessage`/`AiChatMessageSchema`) are unmodified anywhere in this diff — this spec only imports and validates against them.
11. Request handlers stay thin — the Gemini call and Markdown-generation logic live only in `trigger/generate-spec.ts`/`lib/generate-spec-ai.ts`, never inline in either route handler (`architecture-context.md` Invariant 1: "Request handlers do not run long-lived AI work").
12. `npm run build` passes, along with this repo's standard gates (`npx tsc --noEmit`, `npx eslint .`, `npx vitest run`).

### Open questions

1. **What "updates run metadata/status for realtime tracking" concretely requires.** The raw spec text names this as a task responsibility but doesn't specify a mechanism. Two real candidates exist in this codebase: (a) `trigger/design-agent.ts`'s existing pattern of broadcasting to the Liveblocks `ai-status-feed` event (`lib/design-agent-room.ts#broadcastDesignAgentStatus`), which `types/tasks.ts`'s `AiStatusMessage` docblock already notes was kept "generic enough for spec generation's own status broadcasts later"; or (b) Trigger.dev's own native run-metadata mechanism (`metadata.set(...)` from `@trigger.dev/sdk`, consumable client-side through the already-installed `@trigger.dev/react-hooks#useRealtimeRun`, spec 26, with no Liveblocks involvement at all). **Recommendation: (b), Trigger.dev's own metadata mechanism.** Reasoning: the raw text's own wording — "run metadata" — is Trigger.dev's own vocabulary, not how spec 23's text described the Liveblocks mechanism ("broadcast AI status feed events"); this spec's Scope Limits explicitly forbid "frontend logic," and a Liveblocks broadcast is only observable through frontend wiring that doesn't exist for this flow yet; and reusing the single, latest-message-only `ai-status-feed` for a second, structurally different producer (keyed by `roomId` access but not tied to any canvas mutation) risks a viewer being unable to tell which flow's status they're currently seeing. Flagging as a recommendation for the Senior Developer to confirm, not a settled decision — this is the single largest interpretive gap in the spec's text.
2. **Exact Zod shape for `nodes`/`edges`.** `CanvasNode`/`CanvasEdge` are `@xyflow/react`'s `Node<T>`/`Edge<T>` generics with several fields (`id`, `position`, `data`, `width`, `height`, `selected`, etc.) that aren't all relevant to summarizing a graph for Markdown generation. Recommendation: validate a narrower structural subset sufficient for the prompt (id/label/shape/position for nodes; id/source/target/label for edges) — mirroring `lib/design-agent-ai.ts`'s own `DesignAgentGraphNode`/`DesignAgentGraphEdge` summary types, which already take exactly this approach against the same underlying `CanvasNode`/`CanvasEdge` shapes — rather than a brittle, full 1:1 Zod replica of the React Flow type.
3. **`generateText` vs. `generateObject`.** `lib/design-agent-ai.ts` uses `generateObject` + `jsonSchema()` because its output is a bounded, structured action list. This spec's output is free-form Markdown — the raw spec text's own "keep the task output as plain Markdown" instruction. Recommendation: use the `ai` package's `generateText` (not `generateObject`), returning `{ text }` as the task's Markdown output directly — no schema to enforce on the model's response shape.
4. **Whether `lib/trigger.ts`'s token-issuing function should be generalized or duplicated.** `createDesignRunToken(runId)` (spec 22) has no design-specific logic in its own body today — it only scopes a public token to a given `runId` with a fixed expiration. Recommendation: generalize it into a task-agnostic `createRunToken(runId)` and reuse it for both `/api/ai/design/token` and `/api/ai/spec/token`, rather than adding a byte-for-byte duplicate function — `code-standards.md`'s "fix root causes — do not layer workarounds" argues against the duplicate. Flagged as a recommendation touching a spec-22-owned file, not a unilateral decision; renaming is a minor, mechanical, non-behavioral change (the token route callers only care about the return value).
5. **Whether `TaskRun` needs a schema change** (e.g. a `type`/`taskId` discriminator distinguishing a design-agent run from a spec-generation run). Recommendation: no schema change. `TaskRun`'s own docblock already anticipates "future task types," ownership is enforced purely via `userId` regardless of which task produced a given `runId`, and each `runId` is already globally unique per Trigger.dev task invocation — nothing in either spec's acceptance criteria depends on distinguishing run *kind* after the fact.
6. **Whether an empty `nodes`/`edges` graph should be rejected or passed through as-is.** Nothing in the raw spec text or `project-overview.md` describes a minimum-content gate before spec generation. Recommendation: allow it through — Gemini can be prompted to produce a minimal/placeholder spec noting the empty canvas, rather than the route/task inventing a new validation rule not asked for anywhere.
7. **`chatHistory`'s exact type.** Recommendation: `AiChatMessage[]` (`types/tasks.ts`, spec 25), reused unmodified, giving the model the room's full sender/role/content/timestamp chat context — consistent with the raw spec text's own "generates a Markdown technical spec from the canvas and chat context" phrasing and this spec's own Scope Limit against changing existing data models.

### Additional implementation notes (not brief Open Questions)

- **Zod schema sharing between the route and the task**: rather than the route (`app/api/ai/spec/route.ts`) defining its own near-duplicate `nodes`/`edges` Zod schemas, it imports and reuses `trigger/generate-spec.ts`'s own exported `GenerateSpecGraphNodeSchema`/`GenerateSpecGraphEdgeSchema` directly. This means the route's request-body contract and the task's own payload contract can never silently drift apart — a stricter reading of `code-standards.md`'s "fix root causes — do not layer workarounds" than the brief's text explicitly asked for, but a small, mechanical, low-risk choice (both are pure, side-effect-free Zod value exports; no Liveblocks/AI-provider code executes at import time either way, matching the already-proven-safe lazy-instantiation posture `next build`'s page-data collection already relies on for `lib/trigger.ts`/`trigger/design-agent.ts`).
- **`GenerateSpecPayload` as a literal `interface`, not a `z.infer` type alias**: the brief's own concrete-deliverables text names "a `GenerateSpecPayload` interface" specifically (mirroring `DesignAgentPayload`'s own plain-interface shape, no Zod involvement), and `code-standards.md` says "use `interface` for object contracts" — so unlike `types/tasks.ts`'s own `AiChatMessage` (derived via `z.infer<typeof AiChatMessageSchema>`, spec 25's own established pattern), this spec keeps the interface and the Zod schema as two independently-declared, structurally-matching definitions rather than deriving one from the other. `runGenerateSpec`'s own `GenerateSpecPayloadSchema.parse(payload)` call is what keeps them from silently drifting apart in practice — a real runtime check, not just a comment-level assertion.
- **Validation happens outside the task's `try`/`catch` block**: `GenerateSpecPayloadSchema.parse(payload)` runs before the `try` block starts, so a validation failure throws straight up to Trigger.dev's own runtime without ever publishing a `start` status via `metadata.set` — a malformed payload is a caller/integration bug, not a "the run genuinely started and then failed" case, so no misleading in-progress status is ever published for it.
