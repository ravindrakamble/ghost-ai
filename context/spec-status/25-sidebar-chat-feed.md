## Analyst Brief

### Scope statement

Add a second, separate Liveblocks mechanism — `ai-chat` — to the same room the canvas already uses, so participants can send and see ordered, persisted chat messages (sender, timestamp, content) in the AI sidebar's chat area, wired onto the existing sidebar input/Send button from spec 20. This unit is collaborative sidebar chat only: no AI-generated replies, no triggering of `/api/ai/*` routes or Trigger.dev tasks, and no touching of `ai-status-feed`/AI presence (spec 23/24's already-delivered territory).

### Concrete deliverables

- `types/tasks.ts` (modified, additive) — a real **Zod** schema for the chat message shape (`AiChatMessageSchema`, exporting an inferred `AiChatMessage` type via `z.infer`), covering the four fields the spec text names: `sender`, `role`, `content`, `timestamp`. This is the first spec in this codebase to use Zod — specs 22–24 deliberately used manual type guards for their own event payloads because their spec text never named a validation library, but spec 25's text names "Zod schema" twice, so a hand-rolled guard would not honestly satisfy this spec's literal ask (see Open Questions #1). Also exports a validation helper built on the schema (e.g. `AiChatMessageSchema.safeParse`) used both to filter invalid entries out of the rendered feed and, recommended, to validate an outgoing message before it's written to Storage.
- `package.json`/`package-lock.json` (modified) — add `zod` as a new dependency (confirmed genuinely missing from `package.json` today — see Open Questions #1).
- `hooks/use-ai-chat-feed.ts` (new, per `architecture-context.md`'s Hooks Convention) — wraps Liveblocks' `useStorage` to read the room's chat `LiveList`, validates each entry via the Zod schema (dropping anything invalid rather than crashing the sidebar), and returns the ordered, validated message array; also builds a `sendMessage` function on `useMutation` that validates the outgoing message against the same schema before appending it to the `LiveList`. Must be called from inside the room's `RoomProvider` boundary (same constraint spec 24's `useAiStatusFeed` already documents).
- `components/editor/canvas.tsx` (modified) — `RoomProvider` gains an `initialStorage` prop defining the new chat list's root key (e.g. `initialStorage={{ messages: new LiveList([]) }}`), since no `initialStorage` is set today (confirmed by reading the current `RoomProvider` call — it only passes `initialPresence`). `CanvasFlow` calls the new hook, pushes the validated message list up via a new `onChatMessagesChange` callback (mirroring spec 24's `onAiStatusChange` exactly for the "state flows up" direction), and receives/forwards the hook's `sendMessage` function back down as a new prop — the bidirectional counterpart spec 24 didn't need, since that spec only ever consumed a feed, never wrote to one (see Open Questions #3).
- `liveblocks.config.ts` (modified, recommended) — add a `Storage` type to the existing global `Liveblocks` interface augmentation (alongside `Presence`/`UserMeta`) for the new `messages: LiveList<AiChatMessage>` root key, matching this file's own established convention rather than leaving Storage untyped.
- `components/editor/workspace-shell.tsx` (modified) — owns new `chatMessages`/`sendChatMessage` state and callback wiring into `<Canvas>`, mirroring the existing `aiStatus` pattern exactly, then threads both down to `<AiSidebar>` as new props.
- `components/editor/ai-sidebar.tsx` (modified) — forwards the two new props straight through to `<AiArchitectTab>` — no new state owned here, same "pass the real mechanism down as props" posture spec 18/21/24 already established.
- `components/editor/ai-architect-tab.tsx` (modified — a genuine rewrite of this component's message-state ownership, not scope creep): replaces the local-only `useState<ChatMessage[]>` array and its `handleSubmit` push (spec 20) with the real, persisted `chatMessages` prop rendered through the existing `ChatBubble` component (extended to also display `sender` and a formatted `timestamp`, per the spec's "show sender, timestamp, and message content"), and a call to the passed-down `sendMessage` on submit. Clears the input only once the send call completes without error; on failure, preserves the input text and shows a small inline error indicator (recommend the `text-state-error` token, matching `SaveStatusIndicator`'s existing error convention). Starter-prompt-chip fill-not-submit behavior and Enter/Shift+Enter handling are untouched. Spec 20's own docblock already names this exact local array as something "spec 25 owns" — this replacement is the expected next step, not an unplanned rewrite.
- Tests: `types/tasks.test.ts` (extended — Zod schema accept/reject cases for all four fields), `hooks/use-ai-chat-feed.test.ts` (new — subscribes correctly, filters invalid Storage entries, `sendMessage` validates before mutating), `components/editor/ai-architect-tab.test.tsx` (extended — renders persisted messages with sender/timestamp/content, clears input on success, shows error state on failure), `components/editor/canvas.test.tsx`/`workspace-shell.test.tsx`/`ai-sidebar.test.tsx` (extended — new prop/callback threading).
- No changes to `trigger/design-agent.ts`, `lib/design-agent-ai.ts`, `lib/design-agent-room.ts`, `app/api/ai/design*`, `hooks/use-ai-status-feed.ts`, or any `ai-status-feed`/AI-presence code path in `live-cursors.tsx` — spec 23/24's already-delivered territory, untouched by this spec.

### Acceptance criteria

1. A chat `LiveList` (or equivalently named Storage root key) is added to the shared Liveblocks room's Storage, room-scoped, implemented via Liveblocks Storage — not `broadcastEvent` — per `architecture-context.md`'s Realtime Conventions, which pins `ai-chat` to a Storage `LiveList` specifically because it "must replay to participants who join mid-conversation."
2. `types/tasks.ts` exports a real Zod schema (not a hand-written type guard) for the chat message shape, covering at minimum `sender`, `role`, `content`, and `timestamp`, plus a TypeScript type inferred from that schema.
3. The AI sidebar's chat area subscribes to the room's chat Storage via Liveblocks' real `useStorage` mechanism (not polling, not a second websocket, not a parallel realtime system) and renders every message in order, showing sender, timestamp, and content for each message.
4. A user can send a message through the existing sidebar `Textarea`/Send button (no new input UI). On a successful send, the input clears. On a failed send, the input's contents are preserved and a small, visible error indicator appears.
5. Every message read from Storage is validated against the Zod schema before it is rendered; an invalid/malformed entry is dropped (not rendered), and does not crash or blank the rest of the sidebar.
6. `ai-chat` and `ai-status-feed` remain fully independent mechanisms — no shared payload type, no shared subscription, no cross-reading of one feed's data as the other's, and no chat message is ever pushed onto `ai-status-feed` or vice versa.
7. No AI-generated reply is produced anywhere in this diff — every message rendered through this spec's own send path carries `role: "user"`, and `role: "assistant"` remains schema-supported but unreachable through this spec's UI, matching spec 20's own precedent for `ChatBubble`'s assistant branch.
8. No `/api/ai/*` route and no Trigger.dev task is called, triggered, or added anywhere in this diff.
9. No new realtime system outside Liveblocks is introduced (no WebSocket, no Server-Sent Events, no polling loop).
10. `npm run build` passes, along with this repo's standard gates (`npx tsc --noEmit`, `npx eslint .`, `npx vitest run`).

### Open questions

1. **Zod is not currently an installed dependency.** Confirmed by reading `package.json` directly — no `zod` entry exists anywhere in `dependencies` or `devDependencies`. Unlike specs 22/23/24 (which each deliberately used a manual runtime type guard instead of Zod, because their own spec text never named a validation library by name), spec 25's text explicitly says "define or reuse a Zod schema in `types/tasks.ts`" — naming Zod specifically, twice. Recommendation: install `zod` as a new dependency and use a real `z.object({...})` schema, not a manual guard relabeled as one — following the same "the spec's premise didn't hold, install what's actually needed" precedent specs 10/21/22/23 already set for `@liveblocks/node`/`@vercel/blob`/`@trigger.dev/sdk`/`@ai-sdk/google`. Flagging as a recommendation, not a unilateral decision, since it is a new production dependency.
2. **`RoomProvider` currently has no `initialStorage`.** Reading `components/editor/canvas.tsx` directly: `RoomProvider id={roomId} initialPresence={{ cursor: null, thinking: false }}` has no `initialStorage` prop, and no `Storage` type is declared in `liveblocks.config.ts` today — `useLiveblocksFlow` manages nodes/edges without needing a declared root shape. Adding a `messages` Storage root key for chat is additive (it does not touch how nodes/edges are read or written), but it is a change to the one `RoomProvider` instantiation every canvas-related spec since 11 depends on. Recommendation: add `initialStorage={{ messages: new LiveList([]) }}` (exact key name a Dev-level choice) and a matching `Storage` type in `liveblocks.config.ts` for consistency with the existing `Presence`/`UserMeta` convention. Flagging for the Senior Developer to confirm since it touches shared room-initialization code, not because the change itself is expected to be risky.
3. **`AiSidebar` still renders outside the Liveblocks room boundary, and this spec's wiring is now bidirectional.** Spec 24's Open Questions #1 already found that `AiSidebar` has no ancestor `RoomProvider` and recommended a one-directional callback-push-up (`onAiStatusChange`) rather than restructuring the provider tree — sufficient for a read-only feed. This spec both reads (render the message list) and writes (send a message), so the same boundary problem now needs a value flowing **up** (the message list, via a new `onChatMessagesChange` callback, mirroring `onAiStatusChange`) **and** a function flowing **down** (`sendMessage`, built inside `CanvasFlow` via `useMutation` and threaded down through `Canvas` → `WorkspaceShell` → `AiSidebar` → `AiArchitectTab` as a plain prop). Recommendation: extend the existing pattern symmetrically rather than introduce a new mechanism (e.g. a second Liveblocks provider scoped just to the sidebar) — no restructuring of the provider tree, consistent with spec 24's reasoning that doing so would be a much larger, riskier change for no benefit to a sidebar that has nothing to do with canvas rendering. This is the one structurally significant call in this brief, same category spec 24 flagged as its own Open Questions #1 — flagging for the Senior Developer to confirm.
4. **Some field details aren't fully pinned by the spec's own text.** The spec names exactly four fields (`sender`, `role`, `content`, `timestamp`) with no further detail on format or on whether a stable identifier is needed for list rendering. Recommendations: (a) `timestamp` as an epoch-ms `number` (`Date.now()`), a straightforward, sortable, easily-formatted choice — no precedent elsewhere in this codebase pins a different format; (b) `sender` as a display name resolved from the room's own already-resolved identity (Liveblocks `useSelf()`'s `info.name`, the same name `app/api/liveblocks-auth/route.ts` already computes from the caller's Clerk profile at session-auth time), not a raw Clerk user ID, for consistency with how names already surface elsewhere in this room (cursor badges, presence avatars); (c) a message `id` (not one of the spec's four named fields, but needed as a stable React list key once messages can arrive from multiple senders) — recommend adding it as a schema field anyway, since omitting it would force falling back to array index as a key for a live-appending list, which is a known React anti-pattern. All three are Dev-level implementation choices, not product decisions, and none change what's visibly rendered per the spec's own text.
5. **What "failure" means for a Storage-backed send is not specified.** The spec says "show a small error state if sending fails," but a Liveblocks Storage `LiveList` write via `useMutation` is a synchronous, locally-applied, optimistic operation — it doesn't hand back an HTTP-style promise that rejects on failure the way `PUT /api/projects/[projectId]/canvas` (spec 21) does. Recommendation: treat "failure" as (a) the outgoing message failing the Zod schema's own validation before the mutation is attempted, or (b) the mutation call itself throwing synchronously (wrapped in `try`/`catch`) — e.g. calling `sendMessage` while genuinely disconnected from the room. This is a Dev-level interpretation of an otherwise underspecified failure mode, not a literal requirement traceable to specific spec text beyond "show a small error state if sending fails."
6. **Whether `AiArchitectTab`'s existing local-only message state (spec 20) should be fully replaced or run alongside the new persisted feed.** Recommendation: full replacement. Spec 20's own docblock already flags that local `useState<ChatMessage[]>` array as "not a shape any other spec should import (spec 25 owns the real chat message schema in `types/tasks.ts`)" — signaling it was always meant to be superseded once persistence exists, not preserved as a second, parallel message list. Running both simultaneously would produce two independently-ordered message lists competing for the same rendered slot, which conflicts with this spec's own "render chat messages in order" requirement (there is exactly one order to preserve, not two).
