Source spec: `context/feature-specs/38-completion-notifications.md`

## Analyst Brief

### Scope statement

Give a user a visible signal when a design-agent or spec-generation run they submitted finishes while they've navigated away from the tab — a native browser `Notification` when permission has been granted, or a flashing `document.title` otherwise — since `useRealtimeRun`'s state only updates visibly while the sidebar stays mounted and in view. Browser-only, client-local to the submitting user's own tab; nothing else changes.

### Concrete deliverables

- `hooks/use-completion-notification.ts` (new, `"use client"`, per `architecture-context.md`'s Hooks Convention — new client-side hooks live in the top-level `hooks/` folder) — the notification mechanism itself:
  - `notifyCompletion(message: string): void` — the spec's own named entry point. When called while `document.visibilityState === "hidden"`: shows a native `Notification` if the `Notification` global exists and `Notification.permission === "granted"`; otherwise flashes `document.title` (alternating the real title with a short status string) until a `visibilitychange` listener observes the tab becoming visible again, at which point it restores the original title and stops. When called while the tab is visible, it is a no-op — this is what keeps "a user who stays on the tab sees no behavior change from today" true.
  - A second function for requesting permission at the correct moment — see Open Questions #1 for why this can't be the same call as `notifyCompletion` above, despite the raw spec's "exposes a single function" phrasing. Named `requestPermissionOnSubmit()` in this brief; only calls `Notification.requestPermission()` when the `Notification` global exists, `document.visibilityState === "visible"`, and `Notification.permission === "default"` (browsers do not re-show a prompt once a user has explicitly granted or denied it — checking `"default"` is what makes "if permission is denied, never prompt again this session" true for free, off the browser's own persisted state, with no extra bookkeeping needed).
- `components/editor/ai-architect-tab.tsx` (modified) — two call sites, both inside the existing, unmodified control flow:
  - The **run-settled effect** (the `useEffect` starting at line 385, guarded by `isRunSettled`/`handledRunIdRef`, that already calls `pushAgentMessage(...)` with either `resolveSuccessMessage(realtimeRun.output?.summary)` or `buildDesignAgentFailureMessage(realtimeRun.error?.message)`): add one `notifyCompletion(...)` call passing that exact same string, alongside the existing `pushAgentMessage(...)` call.
  - `submitDesignRequest` (the `useCallback` starting at line 400, the function both `handleSubmit` and the "Critique this design" quick action route through via `submitPromptText`): call `requestPermissionOnSubmit()` as the first statement, before the `try` block — the genuine "a generation is actually submitted" moment this file has, guaranteed to run synchronously while the tab is visible (a click handler cannot fire on a hidden tab).
- `components/editor/specs-tab.tsx` (modified) — two call sites, both inside the existing, unmodified control flow:
  - The **completion effect** (the `useEffect` starting at line 225, spec 30, guarded by `isRunSettled`/`handledRunIdRef`, that currently calls `refetch()` on success and `setGenerateError(...)` on failure): add one `notifyCompletion(...)` call reflecting success or failure — see Open Questions #2 for the new success-message text this requires (this file has no existing success-message string to reuse, unlike `ai-architect-tab.tsx`'s `resolveSuccessMessage`).
  - `handleGenerateSpec` (the `useCallback` starting at line 241): call `requestPermissionOnSubmit()` as the first statement, before `setIsSubmittingRun(true)`.

### Acceptance criteria

1. `hooks/use-completion-notification.ts` exports a hook whose return value includes a `notifyCompletion(message: string)` function, matching the raw spec's named deliverable.
2. Calling `notifyCompletion` while `document.visibilityState === "visible"` produces no native notification and no title flash — a user who stays on the tab sees no behavior change from today (raw spec's own "Check When Done" line).
3. Calling `notifyCompletion` while hidden, with `Notification.permission === "granted"`, shows a native browser notification carrying `message`.
4. Calling `notifyCompletion` while hidden, without granted permission (permission is `"default"`/`"denied"`, or the `Notification` API is unavailable in the current browser), instead flashes `document.title` — alternating between the original title and a short status string — until a `visibilitychange` listener detects the tab becoming visible again, at which point the original title is restored and the flash stops.
5. `Notification.requestPermission()` is called only at the moment a design or spec generation is actually submitted (`submitDesignRequest` in `ai-architect-tab.tsx`, `handleGenerateSpec` in `specs-tab.tsx`) and only while the tab is visible — never on initial page load, and never from a hidden tab.
6. Once permission has been explicitly denied, no further `Notification.requestPermission()` call happens for the remainder of the browser session (satisfied by gating the request on `Notification.permission === "default"`).
7. `ai-architect-tab.tsx`'s existing run-settled effect calls `notifyCompletion` with the exact same success/failure text it already pushes onto `ai-chat` via `pushAgentMessage` — no new/divergent message text for the notification path.
8. `specs-tab.tsx`'s existing completion effect (spec 30) calls `notifyCompletion` with a message reflecting the run's success or failure.
9. Neither file's existing on-tab status line/spinner behavior changes (`ai-architect-tab.tsx`'s `isGenerating` status line and busy/disabled state; `specs-tab.tsx`'s "Generate Spec" busy state and inline `generateError` text) — this feature only adds a signal for when the tab is *not* being watched.
10. No email or other server-side notification delivery, no new `app/api` route, no new Trigger.dev task, and no persistent notification history/inbox exist anywhere in this diff.
11. `npm run build` (and this repo's standard mechanical gate — `npx tsc --noEmit`, `npx eslint`, `npx vitest run --no-file-parallelism`) all pass.

### Open questions

1. **The raw spec says the hook "exposes a single `notifyCompletion(message: string)` function," but separately requires that Notification permission be requested "only the first time a generation is actually submitted while the tab is visible" — a different moment (submission) from where `notifyCompletion` is ever actually called (completion, per the wiring steps in sections 2/3, which name only the two completion effects as call sites).** Taken literally, a single function can't serve both: by the time `notifyCompletion` runs at completion, the tab may already be hidden (that's the scenario this whole feature exists for), so requesting permission there would frequently be requesting from a hidden tab — exactly what the spec says never to do.
   **Recommendation:** the hook returns two functions — `notifyCompletion(message)` (the named deliverable, called only at the two completion effects, unchanged) and `requestPermissionOnSubmit()` (called once at the top of `submitDesignRequest`/`handleGenerateSpec`, the two files' own genuine "a generation was just submitted" moments, both synchronous and guaranteed tab-visible). This is a necessary, minimal deviation from the literal "single function" wording to make the explicitly-stated lazy-permission-timing requirement achievable at all — not a scope expansion, since both functions still live in the one new hook file and neither adds new user-facing surface beyond what the spec already describes.

2. **`specs-tab.tsx` has no existing success-message string to reuse for `notifyCompletion` on a successful spec-generation run** (its completion effect currently just calls `refetch()` on success — no chat feed, no message text of any kind — unlike `ai-architect-tab.tsx`, which already has `resolveSuccessMessage`/`DESIGN_AGENT_SUCCESS_MESSAGE`).
   **Recommendation:** add one new local constant, e.g. `SPEC_GENERATION_SUCCESS_MESSAGE = "Your spec has finished generating."`, passed to `notifyCompletion` on the success branch; reuse the already-computed `buildGenerateSpecFailureMessage(realtimeRun.error?.message)` string (already built for `setGenerateError`) on the failure branch, so no new failure-text is invented.

3. **Exact title-flash cadence and status text.** The raw spec gives "✅ Ghost AI is done" only as an illustrative example ("a short status like"), and states no alternation interval.
   **Recommendation:** a fixed, Dev-level constant (e.g. 1000ms alternation), in the same category as this codebase's other unpinned-by-spec timing constants (`ZOOM_TRANSITION_DURATION_MS`, `CANVAS_AUTOSAVE_DEBOUNCE_MS`, `SEARCH_HIGHLIGHT_DURATION_MS`) — any reasonable fixed value satisfies every acceptance criterion above, since none names an exact number. Two concurrent flashes should never stack: a second `notifyCompletion` call while a flash from a prior one is still running should clear the previous interval before starting a new one (mirroring `canvas.tsx`'s own "clear the previous timeout before scheduling a new one" convention from spec 36's search-highlight clearing).
   **Recommendation:** the fallback title-flash text should differ per call site so a returning user can tell *which* run finished — the run-settled/completion effect already has the real message text in hand (design-agent summary/error, or the spec success/failure string from Open Questions #2); a short derived status (e.g. a fixed "✅ Ghost AI is done" for success and "⚠️ Ghost AI hit an error" for failure, rather than the full message text, since a flashing tab title has very limited space) is a reasonable Dev-level choice, not pinned by the raw text.

4. **Native `Notification` constructor shape** — the raw spec says "show a native browser notification with `message`," without specifying whether `message` is the notification's `title` or its `body`.
   **Recommendation:** a fixed, branded title ("Ghost AI") with `message` as the notification's `body` option — the standard way apps surface a dynamic result under a stable identity, and consistent with this codebase's convention elsewhere of a stable branded label plus dynamic content (e.g. `ai-chat`'s bubbles always show a fixed `sender` alongside dynamic `content`).

5. **Whether clicking the native notification should focus the tab.** Not mentioned anywhere in the raw spec text.
   **Recommendation:** not required — leaving the notification's default (dismiss-on-click, no `onclick` handler) is a legitimate, spec-silent minimal implementation; wiring `notification.onclick` to focus the window would be a reasonable enhancement but isn't named by the spec and shouldn't be treated as a missing requirement if omitted (same "minor recommendation, not a literal requirement" posture spec 16's Analyst Brief used for its own marker-hover question).

### Out-of-scope callouts

- **Email or any server-side notification delivery** — explicit Scope Limit in the raw spec text; browser-only (Notification API + title flash), no new backend infrastructure, no new `app/api` route.
- **Persistent notification history/inbox** — explicit Scope Limit; this also rules out reaching for Liveblocks' own separate "Notifications" product feature (referenced only in this repo's bundled `.claude/skills/liveblocks-best-practices` reference docs, never installed/used anywhere in this codebase) — that mechanism is room/thread-based and persisted, which is exactly the "history/inbox" shape this spec explicitly excludes.
- **Requesting Notification permission on page load, or from anywhere other than an actual generation submission** — explicit Scope Limit; no `useEffect` on mount requesting permission.
- **Any change to the existing on-tab status line/spinner behavior** — explicit Scope Limit; `ai-architect-tab.tsx`'s `isGenerating` status line/disabled-input treatment (spec 24) and `specs-tab.tsx`'s "Generate Spec" busy button/inline error (spec 30) are untouched beyond the one new `notifyCompletion` call each.
- **Broadcasting a "run complete" signal to other room participants** — not requested anywhere in the raw spec text ("notify the user," singular, matching that only the submitting client holds the `runId`/`publicToken`/`useRealtimeRun` subscription state for its own triggered run — no other collaborator's client ever reaches either completion effect for a run they didn't submit). This stays a private, per-tab signal to the submitting user only, consistent with `ai-status-feed`/`ai-chat` being separate, already-shipped mechanisms this spec does not touch or extend.
- **Billing, enterprise permission tiers, versioned spec history, production object storage migration, mobile apps** — `project-overview.md`'s Out of Scope wall; none of this spec's work touches any of them.
