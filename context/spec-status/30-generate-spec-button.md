## Analyst Brief

### Scope statement

Wire the Specs tab's existing, inert "Generate Spec" button (`components/editor/specs-tab.tsx`, spec 20/29) to a real spec-generation run: `POST /api/ai/spec` -> `POST /api/ai/spec/token` -> `useRealtimeRun`, mirroring the AI Architect tab's already-shipped trigger/token/subscribe pattern (spec 26), and refresh the spec list on success. Frontend-only — no backend route, Trigger.dev task, or Prisma model changes; this spec's only new capability is closing the generate -> persist -> view -> download loop from the UI.

### Concrete deliverables

- `components/editor/canvas.tsx` (modified, additive) — `CanvasFlow` gains one new `useEffect` pushing the room's live `nodes`/`edges` (the full `CanvasNode[]`/`CanvasEdge[]` React Flow shapes already destructured from `useLiveblocksFlow`) up via a new `onCanvasGraphChange(nodes, edges)` callback prop, mirroring `onChatMessagesChange`'s existing effect-based push exactly (same callback-push-up shape spec 21/24/25 already established for everything only known inside the room boundary). Named `onCanvasGraphChange` — not `onNodesChange`/`onEdgesChange` — to avoid colliding with React Flow's own same-named change-list dispatchers already in scope in this file. `Canvas`'s own prop list and its pass-through to `CanvasFlow` gain the matching prop.
- `components/editor/workspace-shell.tsx` (modified) — owns new `canvasNodes: CanvasNode[]` / `canvasEdges: CanvasEdge[]` state (defaulting to `[]`, mirroring `chatMessages`'s own empty-array default), wired to `<Canvas>` via `onCanvasGraphChange`. Threads `canvasNodes`/`canvasEdges` down to `<AiSidebar>`, alongside the already-owned `chatMessages` (today only forwarded to `AiArchitectTab` — this spec additionally threads that same, already-existing prop value down to `SpecsTab` too; no new chat-related state).
- `components/editor/ai-sidebar.tsx` (modified) — forwards the new `nodes`/`edges` props and the already-received `chatMessages` prop straight through to `<SpecsTab>`, no new state owned here (same "forward straight through" posture this file already follows for every other prop).
- `components/editor/specs-tab.tsx` (modified — the primary site of this spec's logic) — new `nodes: CanvasNode[]`, `edges: CanvasEdge[]`, `chatMessages: AiChatMessage[]` props (alongside the existing `projectId`); new local `runId`/`publicToken`/`isSubmittingRun` state, following `ai-architect-tab.tsx`'s exact pattern (including a `handledRunIdRef`-guarded completion effect and the `realtimeRun.id === runId` staleness guard). The "Generate Spec" button's `onClick` converts the current `nodes`/`edges` into the narrow `{ id, label, shape, x, y }` / `{ id, sourceNodeId, targetNodeId, label? }` structural shape `POST /api/ai/spec`'s body schema expects (a small, pure, client-side mapping — no network call), then runs the two-call trigger/token sequence and subscribes via `useRealtimeRun`. On success, calls `useProjectSpecs`'s existing `refetch()`. On any failure (pre-`runId` POST/token failure, or the run itself settling as failed/errored), shows an inline error near the button (`text-state-error`/`AlertCircle`, matching `ai-architect-tab.tsx`'s/`SaveStatusIndicator`'s existing convention) rather than failing silently. Button shows a spinner (`Loader2`, swapped in place of its label or alongside it) and is `disabled` for the combined "this client's own run is in flight" window (`isSubmittingRun || (runId !== null && !isRunSettled)`) — the same combined-busy convention `ai-architect-tab.tsx` uses, not just the post-broadcast window. Nothing else in the tab (list, preview modal, download actions) is gated by this state.
- Possibly a small pure conversion helper (`CanvasNode[]`/`CanvasEdge[]` -> the narrow spec-request shape) — may live inline in `specs-tab.tsx` (small, single-purpose, matching this file's existing size) or as a small new module if the Senior Developer judges it worth extracting; either is acceptable as long as it stays a pure, synchronous, client-side mapping with no network call (see Open Questions #4/#5 for where its TypeScript types should come from).
- Tests: `components/editor/specs-tab.test.tsx` (extended significantly — trigger/token/run-subscription flow, busy/disabled state, success calling `refetch`, all three failure modes showing an inline error, state reset on settle, the rest of the tab staying interactive during a run), `components/editor/canvas.test.tsx`, `components/editor/workspace-shell.test.tsx`, `components/editor/ai-sidebar.test.tsx` (all extended to cover the new prop-threading chain).
- No file under `app/api/**`, `trigger/**`, `lib/spec-blob.ts`, or `prisma/schema.prisma` touched anywhere in this diff — this spec's own explicit Scope Limit.

### Acceptance criteria

1. Clicking "Generate Spec" calls `POST /api/ai/spec` with `{ roomId: projectId, chatHistory, nodes, edges }`, where `chatHistory`/`nodes`/`edges` are derived from the current room's live chat/canvas state (via the new push-up prop chain), not stale/hardcoded/empty placeholders.
2. On a successful `POST /api/ai/spec`, `POST /api/ai/spec/token` is called with `{ runId }`, and the resulting token is used to subscribe via `useRealtimeRun` (`@trigger.dev/react-hooks`) — the same two-call-plus-subscribe sequence `ai-architect-tab.tsx` already uses for the design agent.
3. The "Generate Spec" button is disabled and shows a busy/spinner state from the moment of click until this client's own triggered run reaches a terminal state — covering both the pre-`runId` window (the two `POST` calls in flight) and the `useRealtimeRun`-tracked window, not just one or the other.
4. While a run triggered from this button is in flight, no other part of the Specs tab (existing spec list, preview modal, per-item download actions) is disabled or visually dimmed.
5. On the run completing successfully, `useProjectSpecs`'s `refetch()` is called so the newly generated spec appears in the list without a manual page reload.
6. On any failure — the initial `POST /api/ai/spec` failing, the token exchange failing, or the subscribed run itself reaching a failed/errored terminal state — an inline error message appears near the "Generate Spec" button; it is not silently swallowed.
7. Local run state (`runId`/`publicToken`) resets to `null` on both the success and failure branch once the run settles, so a subsequent click starts a genuinely new run rather than reusing/getting stuck on stale state (mirrors the spec-26 bugfix already established in `ai-architect-tab.tsx`).
8. No file under `app/api/**`, `trigger/**`, or `prisma/schema.prisma` is touched anywhere in this diff.
9. No Blob URL is fetched or constructed directly by the client anywhere in this change.
10. The design-agent flow (`/api/ai/design*`, `ai-architect-tab.tsx`) is untouched in behavior.
11. The sidebar/tab shell (header, tab triggers, positioning, the existing spec list/preview modal/download UI) is not redesigned — only the Specs tab's own internal "Generate Spec" wiring and the new prop-threading chain change.
12. `npx tsc --noEmit`, `npx eslint .`, `npx vitest run`, and `npx next build` all pass.

### Open questions

1. **Where should the trigger/token/`useRealtimeRun` orchestration logic live — inside `SpecsTab` itself, or lifted up to `WorkspaceShell`?** The raw spec text's own Notes section says to reuse `ai-architect-tab.tsx`'s pattern but doesn't say where the analogous logic should sit in this sidebar's component tree.
   **Recommendation: inside `SpecsTab` itself**, structurally mirroring `AiArchitectTab` exactly (both are siblings under `AiSidebar`, both already sit outside the Liveblocks room boundary, and `SpecsTab` already owns non-trivial local state via `useProjectSpecs`). Lifting the trigger logic into `WorkspaceShell` would mean threading `runId`/`publicToken`/busy-state back down through `AiSidebar` to `SpecsTab` anyway — more prop surface for no benefit — and would arguably violate this spec's own Scope Limit against "new global state beyond what's needed to thread canvas/chat data."

2. **Shape/name of the new nodes/edges push-up callback.** Not specified by the raw spec text beyond "follow the existing callback-push-up pattern."
   **Recommendation: `onCanvasGraphChange(nodes: CanvasNode[], edges: CanvasEdge[])`**, pushed from a dedicated `useEffect` in `CanvasFlow`, structurally identical to `onChatMessagesChange`. Deliberately not named `onNodesChange`/`onEdgesChange` since those names are already React Flow's own change-list-dispatcher convention within the same file, and reusing them here for a completely different payload shape (full snapshots, not change lists) would be misleading.

3. **Does `chatMessages` need new plumbing, or does it just need forwarding one hop further?** `WorkspaceShell` already owns real `chatMessages` state (spec 25) but today only forwards it to `AiArchitectTab` via `AiSidebar`.
   **Resolution (not really an open question, noting it explicitly so it isn't missed): no new state.** `AiSidebar` and `WorkspaceShell` already have the real value; this spec only needs to add `chatMessages` to `SpecsTab`'s prop list and thread the already-existing value one hop further, the same way `projectId` was threaded in spec 26/29.

4. **Client-side conversion from `CanvasNode[]`/`CanvasEdge[]` to the narrow `GenerateSpecGraphNode[]`/`GenerateSpecGraphEdge[]` shape `POST /api/ai/spec`'s Zod schema expects.** Necessary because the room's real nodes/edges are full React Flow objects (`{ id, position: { x, y }, data: { label, shape, color, textColor } }` / `{ id, source, target, data?: { label? } }`), not the flatter `{ id, label, shape, x, y }` / `{ id, sourceNodeId, targetNodeId, label? }` shape the route validates. The raw spec text doesn't name this conversion explicitly (it only says "call `POST /api/ai/spec` with ... `nodes`, and `edges`"), but it's required for the request to pass the route's existing `SpecRequestBodySchema`/`GenerateSpecGraphNodeSchema`/`GenerateSpecGraphEdgeSchema` validation at all.
   **Recommendation: a small, pure, synchronous mapping function** (`node => ({ id: node.id, label: node.data.label, shape: node.data.shape, x: node.position.x, y: node.position.y })`, `edge => ({ id: edge.id, sourceNodeId: edge.source, targetNodeId: edge.target, label: edge.data?.label })`), living directly in `specs-tab.tsx` unless the Senior Developer judges it worth its own small module. No network call, no server-side involvement — this is presentation-layer request-shaping, not business logic that belongs in `lib/`.

5. **Where should the client import the `GenerateSpecGraphNode`/`GenerateSpecGraphEdge` TypeScript types from for that conversion?** They're re-exported from `trigger/generate-spec.ts` (where the matching Zod schemas live, alongside `@trigger.dev/sdk`/`lib/prisma`/`lib/spec-blob.ts` runtime imports), but originally *defined* in `lib/generate-spec-ai.ts`, which `trigger/generate-spec.ts` itself imports them from.
   **Recommendation: type-only import (`import type`) from `lib/generate-spec-ai.ts`**, not `trigger/generate-spec.ts`. A type-only import is erased at compile time either way (no `@ai-sdk/google`/`@trigger.dev/sdk`/Prisma code actually bundles into the client regardless of which file it's sourced from), but importing from `lib/` — the types' real origin — keeps a `components/*` file from having even a type-level import path through `trigger/*`, matching `architecture-context.md`'s system-boundary split (`trigger/` is background-job code, `lib/` is shared infrastructure components are allowed to reference). If the Senior Developer prefers, defining an equivalent small local interface directly in `specs-tab.tsx` (duplicating just the four/three field names, not any logic) is also acceptable — this is a minor, non-blocking style choice, not a correctness issue.

6. **Should an in-flight design-agent run (AI Architect tab) block spec generation, or vice versa?** The raw spec text is silent; its "Button state" section only ever says "a run triggered from this button," not any other flow's state.
   **Recommendation: no cross-tab guard.** Each tab's busy state stays scoped to its own trigger flow, consistent with `ai-architect-tab.tsx`'s own precedent of never gating on anything outside its own `aiStatus`/local-run state.

7. **Should a spec-generation success/failure also push a message onto the shared `ai-chat` feed, the way the design agent does via `sendAgentMessage`?** The raw spec text's "On completion" section only mentions refreshing the list (success) and an inline error near the button (failure) — no mention of chat.
   **Recommendation: no.** Do not call `sendAgentMessage` (or any `ai-chat` write) from this flow. Inventing a chat-feed side effect the spec text never asks for would be scope creep beyond what's written, and the inline-error/list-refresh mechanism the spec does ask for is sufficient to satisfy every "Check When Done" item.

8. **Should the button (or the request) be blocked/warned on an empty canvas (no nodes)?** Not mentioned anywhere in the raw spec text, and the server-side Zod schemas (`z.array(...)`, no minimum length) don't reject an empty graph either.
   **Recommendation: no client-side minimum-node guard.** Defer entirely to whatever `generate-spec-ai.ts`/Gemini already does with an empty graph — adding a new validation rule not requested anywhere would be inventing behavior, not implementing the spec.

If any of the above resolve differently than recommended, that should be recorded explicitly in Dev Notes rather than left implicit.
