Source spec: `context/feature-specs/34-public-share-link.md`

## Analyst Brief

### Scope statement

Let a project **owner** generate (and revoke) a single public, unauthenticated, read-only share link per project, and let anyone with that link view a static snapshot of the project's name, last-saved canvas diagram, and most recent generated spec — with no Liveblocks room join, no live collaboration, and no mutation capability of any kind. Nothing else.

### Concrete deliverables

- `prisma/schema.prisma` (modified) — add `publicShareToken String? @unique` to the `Project` model (nullable — no token means no active link; `@unique` so `app/api/public/[token]/route.ts` can look a project up with a single `findUnique`). A real migration created and applied via `prisma migrate dev`, mirroring spec 33's precedent.
- `app/api/projects/[projectId]/public-link/route.ts` (new):
  - `POST` — owner-only via `lib/projects.ts#getOwnedProjectOrError` (the same gate `PATCH`/`DELETE /api/projects/[projectId]` already use — **not** `getProjectAccess`, per the spec's own explicit instruction and Notes section). Generates a token (`crypto.randomUUID()`, per the spec's own literal example — Node's built-in, cryptographically random, globally available in this runtime, no new dependency), writes it to `Project.publicShareToken`, and returns `{ token }`. Calling `POST` again while a token already exists overwrites it with a fresh one (this is the "regenerate" behavior implied by the task's own "(owner-only, generate/regenerate token)" framing) — the previous token stops resolving immediately, since the old value is gone from the row the moment the new one is written.
  - `DELETE` — owner-only, same gate. Sets `publicShareToken` back to `null`. Returns `{ success: true }`.
  - `GET` — **not named in the spec's own numbered Implementation list**, but required to make the feature usable at all; see Open Questions #1 below for why this is a well-supported addition rather than invented scope, and its exact shape.
  - Failure precedence in all three handlers: 401 (unauthenticated) → 404 (project doesn't exist) → 403 (authenticated non-owner), matching `getOwnedProjectOrError`'s existing contract and `app/api/projects/[projectId]/route.ts`'s own `ownershipErrorResponse` helper (reused or mirrored).
- `app/api/public/[token]/route.ts` (new) — unauthenticated `GET`. `prisma.project.findUnique({ where: { publicShareToken: token } })`; no match → 404 (`errorResponse("Not found", 404)`, per the spec's explicit "do not distinguish wrong token from revoked" instruction). On a match: fetches the canvas snapshot via `lib/canvas-blob.ts#fetchCanvasSnapshot` (reused, not reimplemented, per the spec's own instruction) when `canvasJsonPath` is set, and the most recent `ProjectSpec` row (`orderBy: { createdAt: "desc" }, take: 1`, the same ordering `app/api/projects/[projectId]/specs/route.ts` already establishes for "most recent" — see Open Questions #2) plus its Markdown via `lib/spec-blob.ts#fetchSpecMarkdown` when one exists. Returns `{ projectName, nodes, edges, spec: { markdown, createdAt } | null }` — **never** `ownerId`, collaborator data, `publicShareToken` itself, or any Blob URL (matching the existing canvas/spec routes' own "never return the raw blob URL" convention). Missing canvas/spec are non-error cases (`nodes: [], edges: []` / `spec: null`), not a 404 — see Open Questions #3.
- `app/share/[token]/page.tsx` (new) — a Server Component (default per `code-standards.md`; no browser interactivity needed at the page-shell level) that fetches `GET /api/public/[token]` and renders the static preview. On a non-OK response, renders a simple "This link is invalid or has been revoked" state (via Next's `notFound()` for the 404 case, consistent with this being a genuine not-found page). No Clerk auth check of any kind in this file.
- `components/editor/public-canvas-preview.tsx` (new) — the full-page diagram preview. Reuses `components/editor/starter-template-preview.tsx`'s exported `getTemplateBounds` bounds-fitting helper directly, and mirrors (not imports — `TemplateNodeShape` isn't exported, and a `<div>`-per-shape component can't nest in this SVG-per-shape context any more than `ShapeVisual` could) its per-shape SVG switch/`STROKE` token for `rectangle`/`pill`/`circle`/`diamond`/`hexagon`/`cylinder`, at a page-appropriate size rather than `starter-template-preview.tsx`'s fixed 280×160 card thumbnail — see Open Questions #4 for the exact citation nuance and sizing recommendation. Edges render the same plain `<line>`-between-centers convention (no routing, no arrowheads, no labels — a static preview, not a live edge renderer).
- `components/editor/share-dialog.tsx` (modified) — new "Public link" section, rendered only when `isOwner` is `true` (collaborators, per the spec's explicit Scope Limit, see nothing here — not even a read-only view of whether a link exists). Three states: no link yet (a "Generate public link" button), link exists (the full `/share/{token}` URL plus a Copy button using the exact same `isCopied`/"Copied!"/2-second-timeout convention `handleCopyLink` already implements for the project link, and a "Revoke" button), and in-flight/error states mirroring the collaborator-invite section's existing `Loader2`/inline `text-state-error` conventions.
- `hooks/use-public-link.ts` (new) — `usePublicLink(projectId)`, structurally mirroring `hooks/use-collaborators.ts`'s shape: `{ token, isLoading, error, isGenerating, isRevoking, refetch, generate, revoke }`. No internal auto-fetch effect (same documented reasoning `use-collaborators.ts` already states for avoiding `react-hooks/set-state-in-effect`) — `refetch()` is called from `WorkspaceShell`'s existing `handleOpenShare` handler, alongside the collaborators `refetch()` it already calls, and only when `isOwner` (collaborators have no reason to hit an endpoint that will 403 them).
- `components/editor/workspace-shell.tsx` (modified) — calls `usePublicLink(project.id)` alongside the existing `useCollaborators(project.id)` call, adds its `refetch()` to `handleOpenShare` (gated on `isOwner`), and threads `{ token, isLoading, error, isGenerating, isRevoking, onGenerate: generate, onRevoke: revoke }`-shaped props down to `<ShareDialog>` alongside the props it already passes.
- `proxy.ts` (modified) — `isPublicRoute`'s `createRouteMatcher` array gains two entries: `"/share(.*)"` and `"/api/public(.*)"`. Both are new, unclaimed prefixes (grepped: no existing route under either path) — narrowly scoped so nothing else becomes accidentally public. The existing `config.matcher` already runs every non-static page path and every `/api/*` path through this middleware, so no separate config change is needed beyond the `isPublicRoute` array itself.

### Acceptance criteria

1. `Project.publicShareToken` is a nullable, unique `String` field in `prisma/schema.prisma`, with a real, applied migration. A project with no generated link has `publicShareToken: null`.
2. `POST /api/projects/[projectId]/public-link` requires the caller to be the project **owner** (401 unauthenticated, 404 nonexistent project, 403 authenticated non-owner — including an authenticated *collaborator*, who is explicitly not the owner), generates/overwrites `publicShareToken`, and returns a value the client can build a shareable `/share/{token}` URL from.
3. `DELETE /api/projects/[projectId]/public-link` requires the same owner-only gate, clears `publicShareToken` to `null`, and a subsequent `GET /api/public/[token]` with the old token returns 404.
4. `GET /api/public/[token]` requires no authentication at all, returns 404 for any token with no matching project (identical response whether the token was never valid or was just revoked — no distinguishing signal), and on a match returns the project's name, the last-saved canvas snapshot (if any), and the most recently created spec's Markdown (if any) — never the owner's Clerk ID, never any `ProjectCollaborator` data, never a raw Blob URL, never `publicShareToken` itself.
5. Visiting `/share/[token]` while fully signed out renders the project name, a static read-only diagram matching the last-saved canvas snapshot, and the latest spec's rendered Markdown (if one exists) — with zero edit affordances (no node/edge interaction, no chat, no AI sidebar, no navbar mutation actions) and no Liveblocks room join of any kind.
6. A project with no saved canvas snapshot yet still resolves its public link successfully (not a 404) and shows an explicit empty diagram state rather than an error or a blank/broken render.
7. A project with no generated spec yet still resolves successfully, simply omitting the spec section.
8. An owner can open the Share dialog, generate a public link, see the full URL, and copy it with the same "Copied!" feedback convention `share-dialog.tsx` already uses for the project link.
9. An owner can revoke an existing public link from the Share dialog; the dialog then returns to its "no link yet" state.
10. A signed-in collaborator (non-owner, project member) sees no public-link controls in the Share dialog at all, and a direct `POST`/`DELETE` call against `public-link` from that collaborator's session is rejected with 403.
11. `/share/[token]` and `/api/public/[token]` are reachable while fully signed out (verified against `proxy.ts`'s `isPublicRoute` matcher), and no other route becomes newly public as a side effect.
12. No Liveblocks room token is issued anywhere in this diff's code paths — `architecture-context.md`'s "room tokens require verified project membership" invariant is untouched (`app/api/liveblocks-auth/route.ts` is not modified).
13. `npm run build` (and this repo's established mechanical gate — `npx tsc --noEmit`, `npx eslint`, `npx vitest run --no-file-parallelism`) all pass.

### Open questions

1. **The spec's Implementation section only names `POST`/`DELETE` for `public-link`, with no `GET` — but nothing in the raw spec text explains how the Share dialog is supposed to know, when it opens, whether a public link already exists for this project (to show "Copy/Revoke" instead of "Generate").** `WorkspaceShell`'s `project` prop (from `getProjectAccess`, typed via `types/project.ts`'s `Project = { id, name }`) does not carry `publicShareToken`, and `ShareDialog`'s existing collaborator section already establishes the precedent of a dedicated `refetch()`-on-dialog-open call rather than a server-rendered initial value.
   **Recommendation:** add a `GET` handler to the same `app/api/projects/[projectId]/public-link/route.ts` file the spec already names (not a new file, not a change to the widely-shared `getProjectAccess`/`types/project.ts`), owner-only via the identical `getOwnedProjectOrError` gate, returning `{ token: string | null }`. `hooks/use-public-link.ts#refetch()` calls it exactly the way `useCollaborators#refetch()` is already called from `WorkspaceShell#handleOpenShare`. This is the narrowest change that makes the feature actually usable, stays inside the one file the spec's own text already scopes for this route, and reuses an access-check pattern already fully proven for this exact route.

2. **What "latest spec" means precisely.** The raw spec text says "the most recent `ProjectSpec` row if any" with no explicit ordering field named.
   **Recommendation:** most recent `createdAt` (`orderBy: { createdAt: "desc" }, take: 1`) — the identical ordering `GET /api/projects/[projectId]/specs/route.ts` already uses for "newest first," and the only ordering field `ProjectSpec` has (no separate "latest"/"published" flag exists on the model). Not genuinely ambiguous given that precedent, but stated explicitly since the spec text itself doesn't name a field.

3. **How a missing or stale canvas snapshot should degrade.** The spec says "fetches the latest canvas snapshot... returns just enough to render a read-only view," but doesn't address the case where `canvasJsonPath` is `null` (nothing ever saved) or `fetchCanvasSnapshot` itself returns `null` (blob missing/corrupt — the same "nothing usable is there" case `GET /api/projects/[projectId]/canvas` already treats as its own 404). Since the *token* is still valid and the *project* still exists, collapsing this into the route's own 404 would incorrectly read to a visitor as "this link is broken," which it isn't.
   **Recommendation:** `GET /api/public/[token]` treats a missing canvas as a non-error case — `nodes: []`, `edges: []` in the response, never a 404 — and `app/share/[token]/page.tsx`/`public-canvas-preview.tsx` render an explicit "No diagram has been saved for this project yet" empty state (the same posture `getTemplateBounds` already takes for a zero-node array, extended with a visible text state rather than silently rendering an empty SVG). A genuine upstream Blob failure (network/auth error, not "nothing there") should still be allowed to throw and surface as a 500, matching `fetchCanvasSnapshot`'s own documented not-found-vs-genuine-failure distinction.

4. **The spec's Notes section attributes the reusable "bounds-fitting/shape-drawing helpers" to `starter-templates-modal.tsx`, but they actually live in `components/editor/starter-template-preview.tsx`** (`getTemplateBounds` is exported from there; the modal only consumes `<StarterTemplatePreview>` as a component, it doesn't itself define any bounds/shape logic). Separately, `starter-template-preview.tsx`'s `PREVIEW_WIDTH`/`PREVIEW_HEIGHT` (280×160) are sized for a card thumbnail inside a grid, not a full-page primary view, and its internal `TemplateNodeShape` component/`STROKE` constant aren't exported.
   **Recommendation:** treat this as a minor citation slip in the spec text, not a different set of files to reuse. Import and reuse `getTemplateBounds` directly from `starter-template-preview.tsx`. For the per-shape drawing, mirror (don't attempt to import) the same switch-case/`STROKE`-token approach into the new `public-canvas-preview.tsx`, at a larger, page-appropriate fixed size (Dev's call — nothing in the spec text pins an exact number, the same "reasonable unpinned value" precedent as `NODE_MIN_SIZE`/`CANVAS_AUTOSAVE_DEBOUNCE_MS`) — e.g. large enough to fill most of the page body rather than a card slot, using the same `viewBox`/default `preserveAspectRatio` ("`xMidYMid meet`") idiom so the diagram's real proportions are preserved regardless of the exact pixel dimensions chosen.

5. **Whether `POST /api/projects/[projectId]/public-link` should return a fully-qualified absolute URL or just the raw token.** The spec's own text says the route "returns the shareable URL," but this codebase has no existing server-side origin-resolution mechanism (no `NEXT_PUBLIC_APP_URL`-style env var, no `request.nextUrl.origin` usage anywhere) — the only existing precedent for building a shareable link (`share-dialog.tsx#handleCopyLink`, spec 09) constructs it entirely client-side via `window.location.origin`.
   **Recommendation:** the route returns `{ token }` (the raw value), and the client (`hooks/use-public-link.ts` / `ShareDialog`'s new section) builds the displayed/copied URL the same way `handleCopyLink` already does — `` `${window.location.origin}/share/${token}` `` — rather than introducing a new server-side origin-resolution mechanism this codebase has never needed before. Functionally satisfies "returns the shareable URL" (the owner always ends up with a real, correct, copyable URL) without new infrastructure.

6. **Whether `GET /api/public/[token]` needs its own rate limiting, given spec 31 exists.** The task explicitly asks this to be flagged. `lib/rate-limit.ts#checkAiRateLimit` is keyed by authenticated Clerk `userId` against `TaskRun` rows — it has no meaning for an anonymous caller, and spec 31's own Scope Limits confine it to `POST /api/ai/design`/`POST /api/ai/spec` only. No general per-IP or per-token request-rate-limiting mechanism exists anywhere else in this codebase.
   **Recommendation:** out of scope for this spec. Nothing in spec 34's text requests rate limiting, and building one (per-IP throttling, a new store, etc.) for a read-only, non-AI, non-billed endpoint would be inventing infrastructure not asked for anywhere — exactly what `ai-workflow-rules.md`'s "do not invent product behavior" guards against. Recommend logging this as a named item in `progress-tracker.md`'s production-hardening backlog (this endpoint is the first fully unauthenticated data-serving route in the app, and an unrevoked link is effectively public forever) rather than building it now.

### Out-of-scope callouts

- **Joining the Liveblocks room for public viewers, or any live/real-time view.** Explicit Scope Limit in the raw spec text — the public page renders the last persisted snapshot only, via a plain `fetch()`, never a `RoomProvider`/`useStorage`/presence of any kind.
- **Any mutation from the public page** — no node/edge editing, no chat, no AI sidebar, no navbar actions of any kind. `app/share/[token]/page.tsx` renders no interactive canvas component (`CanvasFlow`/`@xyflow/react`) at all, only the new static SVG preview.
- **Exposing collaborator emails or the owner's identity on the public page or its backing API response** — explicit Scope Limit; `GET /api/public/[token]`'s response shape deliberately excludes `ownerId` and any `ProjectCollaborator` data.
- **Changing how Liveblocks room tokens are issued for authenticated collaborators** — explicit Scope Limit; `app/api/liveblocks-auth/route.ts` is untouched by this diff.
- **Collaborators generating or revoking the public link** — explicit Scope Limit; owner-only on all three `public-link` methods (including the newly-added `GET`, per Open Questions #1).
- **A general anonymous-request rate-limiting system** — not requested by the raw spec text; see Open Questions #6. Only the specific, narrow gap the task asked about is flagged, not built.
- **A "sign in to edit" call-to-action, branding, or any other content beyond project name / diagram / latest spec on the public page** — not mentioned anywhere in the raw spec text; adding one would be inventing UX not asked for.
- **Billing, enterprise permission tiers, versioned spec history, production object storage migration, mobile apps** — `project-overview.md`'s Out of Scope wall; none of this spec's work touches any of them. In particular, this spec does not add a "link expiration" or "view count" concept — the spec text describes only generate/revoke, nothing time-boxed or metered.
- **Any change to `components/editor/starter-template-preview.tsx`, `starter-templates-modal.tsx`, or `starter-templates.ts`** — the new `public-canvas-preview.tsx` mirrors that file's geometry/bounds approach but is a separate file; the existing template-preview component and its 280×160 card sizing are untouched.

### Database migration — a note on how it was applied

Running `prisma migrate dev` against the shared dev Postgres database reported drift: `CustomTemplate` (spec 33's own model) is already applied live on this shared database (spec 33 ran its own `migrate dev` against the same instance before its PR was merged), but that migration isn't in `main`'s (or this branch's) local `prisma/migrations/` history, since spec 33 hasn't merged. `prisma migrate dev`'s own remediation path for this is `migrate reset`, which would drop `CustomTemplate` and its data — an unrelated, in-flight branch's work, and a destructive action never taken without explicit consent per this pipeline's Git Safety Protocol.

Instead: hand-wrote this spec's own migration SQL (`ALTER TABLE "Project" ADD COLUMN "publicShareToken" TEXT; CREATE UNIQUE INDEX ...`, matching this repo's existing `TaskRun.runId` unique-column migration pattern exactly), applied it directly via `prisma db execute --file ...`, then recorded it as applied via `prisma migrate resolve --applied ...`. `prisma migrate status` reports clean afterward. `prisma/schema.prisma` on this branch does **not** declare `CustomTemplate` (that stays spec 33's own deliverable) — only `Project.publicShareToken` was added, so this branch's schema/migration diff is scoped to spec 34 alone. The live database physically also has the unrelated `CustomTemplate` table sitting unused from spec 33's own migration; that's a pre-existing environmental fact of the shared dev database, not something this diff introduces or is responsible for reconciling.
