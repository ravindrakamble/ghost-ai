Source spec: `context/feature-specs/37-node-comments.md`

## Analyst Brief

### Scope statement

Add async, node-scoped comment threads — a flat, chronological, persisted list of comments per canvas node, discoverable via a small badge/trigger on the node itself and viewable/addable through a popover — distinct from live cursors/presence (spec 19) and the room-wide `ai-chat` feed (spec 25). Nothing else changes.

### Concrete deliverables

- `liveblocks.config.ts` (modified) — the room's `Storage` type gains a second field, `nodeComments: LiveList<NodeComment>`, alongside the existing `messages: LiveList<AiChatMessage>` (spec 25) — same flat-`LiveList`-per-feed shape, not a new `LiveMap`-per-node structure. Every entry carries its own `nodeId`, so one list serves every node in the room, matching the raw spec text exactly.
- `types/tasks.ts` (modified, additive) — `NodeCommentSchema` (Zod): `{ id, nodeId, sender, content, timestamp }` — the same field shape as `AiChatMessageSchema` plus `nodeId`, kept as a fully independent schema/type with **no shared base type** with `AiChatMessage` (matching this codebase's existing convention of independent per-feed types, e.g. `AiStatusMessage` vs. `AiChatMessageSchema` staying unrelated). Also exports the inferred `NodeComment` type and a `SendNodeComment` function-shape type (`(nodeId: string, content: string) => void`), mirroring `SendChatMessage`'s own doc/contract conventions (synchronous, throws on invalid outgoing data).
- `hooks/use-node-comments.ts` (new) — three exports:
  - `useNodeComments()`: mirrors `hooks/use-ai-chat-feed.ts#useAiChatFeed`'s exact internal shape — reads `root.nodeComments` via `useStorage`, validates every entry through `NodeCommentSchema.safeParse` inside a `useMemo` (dropping invalid entries, never rendering/crashing on one), and builds `sendComment` via `useCallback` wrapping a `useMutation`-built push, with `sender` resolved from a narrowly-selected `useSelf((me) => me.info.name)` (the same narrow-selector convention `useAiChatFeed` itself uses, and for the same documented reason — an unselected `useSelf()` re-renders, and gives the returned function a new identity, on every presence/cursor update). Returns `{ comments: NodeComment[]; sendComment: SendNodeComment }`. Called exactly once, inside `CanvasFlow` — see Open Questions #3 for why this is not parameterized per-node and not called directly inside every `CanvasNode` instance.
  - `NodeCommentsContext` — `React.createContext<{ comments: NodeComment[]; sendComment: SendNodeComment } | null>(null)`, structurally mirroring `hooks/use-update-canvas-node.ts`'s `CanvasNodeUpdateContext`/`hooks/use-canvas-search-highlight.ts`'s `CanvasSearchHighlightContext` pair — context provided by `CanvasFlow`, consumed by a leaf component, per `architecture-context.md`'s Hooks Convention.
  - `useNodeCommentsForNode(nodeId: string)`: the leaf-facing consumer hook, called by `NodeCommentsPopover`. Reads `NodeCommentsContext`, `useMemo`-filters the full `comments` list down to just this `nodeId` (client-side filtering happens here, not inside `useNodeComments()` itself — see Open Questions #3), and returns a nodeId-bound `sendComment(content: string)` plus the filtered `comments`. Returns an empty list and a throwing stub `sendComment` when called with no provider in the tree (mirroring `chatNotReadyYet`'s "not ready yet" contract in `ai-architect-tab.tsx`, not `useCanvasSearchHighlight`'s silent-`null` default — a comment send attempted with no real mutation behind it should surface as a genuine failure, not a silent no-op).
- `components/editor/canvas.tsx` (modified) —
  - `RoomProvider`'s `initialStorage` gains `nodeComments: new LiveList([])`, matching exactly how `messages` was added for spec 25.
  - `CanvasFlow` calls `useNodeComments()` once (valid here for the same reason `useAiChatFeed()`/`useAiStatusFeed()` already are — `CanvasFlow` sits inside `RoomProvider`) and wraps its returned `{ comments, sendComment }` in a new `<NodeCommentsContext.Provider>`, nested alongside the existing `CanvasNodeUpdateContext`/`CanvasEdgeUpdateContext`/`CanvasSearchHighlightContext` providers (spec 36's own precedent for a fourth nested provider). No push-up to `WorkspaceShell` — like search-highlight state, node comments have no consumer outside the room-bounded `CanvasFlow` subtree.
- `components/editor/node-comments-popover.tsx` (new) — `NodeCommentsPopover({ nodeId }: { nodeId: string })`:
  - A trigger element (badge/popover-trigger combined, per the raw spec's own "badge/popover trigger" phrasing) built on the existing `components/ui/popover.tsx` primitive (`Popover`/`PopoverTrigger`/`PopoverContent`, added by spec 36) — reused as-is, not modified, not duplicated with a second popover-like primitive (see Open Questions #2).
  - `PopoverContent` renders the node's own comment thread in chronological order (from `useNodeCommentsForNode(nodeId)`), each entry as a small bubble showing sender + formatted timestamp + content — mirroring `ChatBubble`'s sender/timestamp/content *layout convention* from `ai-architect-tab.tsx` (per the raw spec's own instruction), not a literal reuse of the `ChatBubble` component itself (see Open Questions #6), plus a small reply input (`Textarea` + Send `Button`, Enter-without-Shift submits) calling `sendComment(content)`.
  - An empty-thread state ("No comments yet.") when the node has zero comments, since the reply input must still be reachable to write the first one (see Open Questions #1).
- `components/editor/canvas-node.tsx` (modified, minimal) — renders `<NodeCommentsPopover nodeId={id} />` as one more sibling inside the existing `group relative` wrapper `<div>` (the same wrapper `ShapeVisual`, the four connection `Handle`s, and spec 36's highlight-ring class already share) — the *only* change this spec makes to this file, per its own explicit Scope Limit. See Open Questions #4 for exact placement/visual treatment.

### Acceptance criteria

1. `liveblocks.config.ts`'s `Storage` type gains `nodeComments: LiveList<NodeComment>`, alongside the existing `messages` field — same flat `LiveList`-per-feed shape as `ai-chat`.
2. `types/tasks.ts` defines `NodeCommentSchema` (Zod) with `{ id, nodeId, sender, content, timestamp }` and its inferred `NodeComment` type — the same field shape as `AiChatMessageSchema` plus `nodeId`, with no shared base type between the two schemas.
3. `hooks/use-node-comments.ts#useNodeComments()` reads/validates the `nodeComments` `LiveList` via `useStorage`, drops any entry that fails `NodeCommentSchema.safeParse` (never renders/crashes on an invalid entry), and exposes `sendComment(nodeId, content)` built via `useMutation` with `sender` resolved from `useSelf` — mirroring `use-ai-chat-feed.ts#useAiChatFeed`'s exact internal shape.
4. `RoomProvider`'s `initialStorage` in `components/editor/canvas.tsx` includes `nodeComments: new LiveList([])`.
5. A node with one or more comments shows a persistent, visible indicator (a small count badge) rendered from `canvas-node.tsx`.
6. Clicking the trigger opens a `Popover` (`components/ui/popover.tsx`, the existing primitive — no new/duplicate popover component) scoped to that node's own comment thread, rendered in chronological order.
7. Comments on different nodes never mix in the same thread view — the thread rendered for node A never shows an entry whose `nodeId` is not A's own id.
8. The popover includes a reply input; submitting calls `sendComment(nodeId, content)`, and the new comment persists in Liveblocks Storage and replays correctly to a participant who joins the room afterward.
9. A node with zero comments still has a reachable way to start its own first thread (the trigger itself is always present/clickable, not only the count badge) — see Open Questions #1 for why the raw spec's literal "badge only when count ≥ 1" wording needed this resolution.
10. `canvas-node.tsx`'s existing drag, resize, label-edit, select, and connection-handle behavior is unmodified — the only diff in that file is the new `<NodeCommentsPopover>` addition.
11. No threaded replies/replies-to-replies UI, no @mentions or notification mechanism, and no edge-comment capability exist anywhere in this diff.
12. `ai-chat` (`hooks/use-ai-chat-feed.ts`, the `messages` Storage field) and `ai-status-feed` are byte-for-byte untouched by this diff.
13. `npm run build` (and this repo's standard mechanical gate — `npx tsc --noEmit`, `npx eslint`, `npx vitest run --no-file-parallelism`) all pass.

### Open questions

1. **How does a node with zero comments ever get its first comment?** The raw spec text says the badge shows "when it has one or more comments," but names no other entry point for starting a thread — taken literally, a node at zero comments would have no reachable UI to write the first one.
   **Recommendation:** the trigger element is always present and clickable (the badge and the popover trigger are the same element, per the spec's own "badge/popover trigger" phrasing) — at zero comments it renders icon-only, hidden at rest and revealed on node hover (the exact same `opacity-0 group-hover:opacity-100` convention `canvas-node.tsx` already uses for its four connection handles); once the node has ≥1 comment, it becomes unconditionally visible (`opacity-100`) with a numeric count badge — satisfying acceptance criterion 5's "persistent visible indicator" literally, while still leaving a reachable way to start a first thread.

2. **Should the new component reuse spec 36's `Popover` primitive, or a different shadcn component?** Not addressed by the raw spec text.
   **Recommendation:** reuse `components/ui/popover.tsx` as-is (a protected foundation component per `ai-workflow-rules.md` — used, not redesigned or duplicated). It already provides exactly the "small trigger + anchored floating content" shape this feature needs; adding a second, functionally-near-identical popover primitive (or reaching for `Dialog`, which this codebase reserves for centered/modal-scale content like `ShareDialog`/`StarterTemplatesModal`) would be an unjustified duplication.

3. **Where should comment filtering-by-`nodeId` live: inside a parameterized `useNodeComments(nodeId)`, or as a full-list export with filtering left to the caller?** The raw spec text explicitly leaves this as "implementer's choice."
   **Recommendation:** full-list export, filtered by the caller — `useNodeComments()` (no parameter) is called exactly once, inside `CanvasFlow` (mirroring `useAiChatFeed()`'s own single call site), and its result is distributed to every `CanvasNode` leaf via a new `NodeCommentsContext` — the same single-subscription-then-Context-fan-out architecture this file already uses three times (`CanvasNodeUpdateContext`, `CanvasEdgeUpdateContext`, `CanvasSearchHighlightContext`). The alternative — a parameterized `useNodeComments(nodeId)` called directly inside each of N node instances — is technically legal (`CanvasNode` already renders inside the `RoomProvider` boundary) but would mean N independent `useStorage` subscriptions each re-validating the *entire* comment list on every change, an inefficiency this codebase has already shown active awareness of and fixed once before (`use-ai-chat-feed.ts`'s own narrowed-`useSelf`-selector change, made specifically to stop a re-render cascade). A thin `useNodeCommentsForNode(nodeId)` consumer hook (in the same file) does the actual per-node `useMemo` filter against the Context's already-validated list, keeping `NodeCommentsPopover`'s own call site a single line.

4. **Exact badge/trigger placement and visual treatment on `canvas-node.tsx`.** Not addressed by the raw spec text.
   **Recommendation:** `absolute -top-2 -right-2 z-20` on the node's existing `group relative` wrapper (the same wrapper `NodeColorToolbar`, the connection handles, and spec 36's highlight ring already attach to) — a small `rounded-full`/`bg-elevated`/`border-surface-border` pill (matching the edge-label-pill and `+N`-overflow-chip visual language already established elsewhere in this codebase) containing a `MessageCircle` icon (`h-3 w-3`) and, once count ≥ 1, the numeric count in `text-copy-primary`. Carries `nodrag nopan` so clicking it never starts a node drag. **Known, disclosed, non-blocking overlap:** `NodeResizer`'s own top-right corner resize handle occupies roughly the same corner when a commented node is *also* currently selected — both affordances are independently correct in their own gating condition (comment count vs. `selected`), and this is a Dev-level z-index/offset call to make both remain clickable, not a design defect to route back through this brief.

5. **How should the popover's open/close state be scoped: per-node local state, or a single "which node's thread is open" piece of state owned by `CanvasFlow` (mirroring spec 36's highlight-state scoping)?**
   **Recommendation:** per-node local state, owned by `NodeCommentsPopover` itself (the `Popover` primitive's own local open state). Unlike spec 36's search-highlight state — which is inherently a single, cross-node value (only one node can be "the current jump target" at a time, computed by an imperative handler in `CanvasFlow`) — a node's own comment-thread open/closed state has no cross-node coordination requirement: opening node A's thread has no bearing on node B's. Centralizing it in `CanvasFlow` would add a state-lifting indirection (and route every reply-input keystroke back up through a context) for no behavioral benefit.

6. **Literal `ChatBubble` reuse vs. mirroring only its layout convention.** The raw spec says "reuse `ChatBubble`'s sender/timestamp/content layout convention," but `ChatBubble` branches its left/right alignment and border/background color on `AiChatMessage.role` (`"user" | "assistant"`) — a field `NodeCommentSchema` deliberately does not have (per its own "same field shape as `AiChatMessageSchema` plus `nodeId`," listing only `{ id, nodeId, sender, content, timestamp }`).
   **Recommendation:** a small, new, uniformly-styled bubble defined locally in `node-comments-popover.tsx` — sender name + formatted timestamp header row, content below, `rounded-2xl`/`border-surface-border`/`bg-subtle`/`text-copy-primary`, left-aligned for every entry (no role-based split, since there is no role concept for a comment) — genuinely mirroring `ChatBubble`'s visual *convention* as the spec's own text asks, without importing or repurposing a component built around a field this schema doesn't carry.

### Out-of-scope callouts

- **Threaded replies / replies-to-replies** — explicit Scope Limit in the raw spec text; a flat, chronological list per node only.
- **@mentions or any notification mechanism** — explicit Scope Limit; the raw spec text itself points at "the 'notify on completion' idea" (spec 38, `context/feature-specs/38-completion-notifications.md`, still an unstarted raw draft) as a separate, later concern — not pulled forward into this spec.
- **Comments on edges** — explicit Scope Limit; nodes only, no `CanvasEdgeData` involvement.
- **Any change to `ai-chat` or `ai-status-feed`** — explicit Scope Limit; both stay byte-for-byte untouched (acceptance criterion 12).
- **Any change to `canvas-node.tsx`'s drag/select/edit behavior beyond the badge/popover trigger** — explicit Scope Limit; the only permitted diff is the new `<NodeCommentsPopover>` addition.
- **Comment editing or deletion** — not requested anywhere in the raw spec text; an append-only `LiveList`, matching `ai-chat`'s own append-only precedent exactly, with no update/delete mutation or UI.
- **A new `app/api` route or Prisma model** — comments live entirely in Liveblocks Storage, already governed by the existing room-token auth (`architecture-context.md`: "Liveblocks room tokens are issued only after verifying project membership"); no server-side persistence layer is added by this spec.
