# Spec 23: Design Agent Logic

Source spec: `context/feature-specs/23-design-agent-logic.md`

## Analyst Brief

### Scope statement

Implement the real body of the `design-agent` Trigger.dev task: interpret the user's prompt with Gemini (`@ai-sdk/google`), turn the result into a bounded set of canvas actions (add/move/resize/delete node, update node data, add/delete edge), apply them to the project's Liveblocks room through the same Storage schema the client-side canvas already uses, and broadcast AI status (`ai-status-feed`) and AI presence (`thinking`/`cursor`) around that work — all from server-side Node.js code running inside the Trigger.dev task, not from a React component. Nothing else changes: the `POST /api/ai/design`/`POST /api/ai/design/token` routes and the `TaskRun` model (spec 22) are untouched, and no sidebar/chat/status UI is built here (that is specs 24/25/26).

### Concrete deliverables

- `trigger/design-agent.ts` (modified) — `runDesignAgent` gains the real implementation. The `logger.log`/echo shell from spec 22 is replaced with: read current canvas state → call Gemini for a structured list of actions → apply those actions to the room's Liveblocks Storage → publish status/presence around the work → handle failures without leaving the canvas or the status feed in a broken state. Exact internal structure (how much logic stays in this file vs. is factored into `lib/`) is a Senior Developer call, but per `code-standards.md`'s "keep modules small and single-purpose," the AI-interpretation step and the Liveblocks-server-mutation step should not be one undifferentiated block.
- New `lib/` module(s) (exact names/count are a Dev call, but the boundary is real, not optional):
  - A Gemini/AI-interpretation module — wraps the `@ai-sdk/google` + `ai` call that turns `{ prompt, current nodes/edges }` into a validated list of actions.
  - A Liveblocks-server-mutation module (or an extension of `lib/liveblocks.ts`) — wraps `getLiveblocksClient().mutateStorage(...)` / `.broadcastEvent(...)` / `.setPresence(...)` / `.getStorageDocument(...)` calls specific to the design agent's needs, reusing `getLiveblocksClient()` from spec 10 rather than constructing a second Liveblocks Node client.
- `package.json`/`package-lock.json` — add `@ai-sdk/google` and `ai` (the core Vercel AI SDK package `@ai-sdk/google` is a provider for, not a standalone caller — see Open Questions #1). Neither is currently installed.
- `.env.local` — add a real `GEMINI_API_KEY` (currently absent — see Open Questions #2), following the same "lazy read, not read at import time" posture already established for `TRIGGER_SECRET_KEY`/`LIVEBLOCKS_SECRET_KEY`/`BLOB_READ_WRITE_TOKEN` so a missing key doesn't break `next build`.
- Tests: `trigger/design-agent.test.ts` (rewritten — the spec-22 echo-only assertions no longer apply), plus new test files for whatever `lib/` module(s) are added, mocking `@ai-sdk/google`/`ai` and the relevant `@liveblocks/node` client methods via `vi.mock`/`vi.hoisted`, per `code-standards.md`'s Testing section.
- No changes to `app/api/ai/design/route.ts`, `app/api/ai/design/token/route.ts`, `prisma/schema.prisma`, or any `components/*` file — this spec's own Scope Limits ("don't change canvas architecture," "don't bypass existing collaborative flow utilities") and its focus on `trigger/design-agent.ts` keep it there.

### Acceptance criteria

1. `runDesignAgent` calls Gemini (`@ai-sdk/google`, via the `ai` package) to interpret `payload.prompt` — no other AI provider, and no hardcoded/templated "fake AI" response.
2. Before generating actions, the task reads the room's **current** Liveblocks Storage content (via `getLiveblocksClient().getStorageDocument(roomId)` or equivalent), not the spec-21 Vercel Blob autosave snapshot (which can lag up to `CANVAS_AUTOSAVE_DEBOUNCE_MS` behind live edits) — satisfying `architecture-context.md`'s "Input: user prompt, project context, and current canvas state."
3. Generated actions are limited to exactly the seven kinds the spec lists: add node, move node, resize node, update node data, delete node, add edge, delete edge. No other canvas mutation (e.g., a wholesale clear-and-replace) happens.
4. Every AI-generated node's `shape` is one of `CANVAS_SHAPES` (`lib/canvas-shapes.ts`) and every `color`/`textColor` pair is one of `NODE_COLORS` (`types/canvas.ts`) — no invented shape or color value reaches Storage.
5. Every AI-generated node's size is derived from `SHAPE_DEFAULT_SIZES`/respects `NODE_MIN_SIZE` (`lib/canvas-shapes.ts`) — no node smaller than the existing floor or a shape-inappropriate default size.
6. Canvas mutations are written into the room's Liveblocks Storage through the same schema `useLiveblocksFlow` reads/writes client-side (default `storageKey: "flow"`, a `LiveObject` with `nodes: LiveMap<string, …>` / `edges: LiveMap<string, …>`, confirmed directly against the installed `@liveblocks/react-flow` types and `components/editor/canvas.tsx`'s real, unmodified `useLiveblocksFlow<CanvasNodeAlias, CanvasEdgeAlias>({...})` call, which passes no custom `storageKey`) — so a connected client's existing hook picks the change up with no client-side code change.
7. A status message is broadcast to `ai-status-feed` (via `getLiveblocksClient().broadcastEvent(roomId, message)`) at minimum at three points: start, in-progress/processing, and completion — matching the spec's explicit "start, processing, complete" language.
8. AI presence (`thinking: true`, per the pinned `Presence` shape in `liveblocks.config.ts`) is set for the duration of the run via `getLiveblocksClient().setPresence(roomId, { userId, data, userInfo, ttl })` — the Node SDK method whose own doc comment names this exact use case ("showing an AI agent's presence in a room") — and is cleared (`thinking: false`, cursor `null`, or an expired TTL) once the task finishes, whether it succeeds or fails.
9. On any failure (Gemini call fails, response fails validation, a Liveblocks mutation fails), the task broadcasts an error status message to `ai-status-feed`, clears AI presence, and does not leave the room's canvas Storage partially mutated in a way that breaks the client-side renderer (`CanvasNode`/`CanvasEdge` must never receive a shape/color/data value outside the vocabulary in criteria 4–5) — matching "handle errors gracefully" and "errors are handled without breaking the canvas."
10. No `components/*` file is touched, no new Liveblocks package is added, and no canvas mutation happens outside the Storage schema criterion 6 describes — satisfying this spec's own Scope Limits ("don't change canvas architecture," "don't introduce a new state system outside Liveblocks," "don't bypass existing collaborative flow utilities").
11. `npm run build` passes, along with this repo's other standard gates (`npx tsc --noEmit`, `npx eslint .`, `npx vitest run`) — including with no `GEMINI_API_KEY`/`TRIGGER_SECRET_KEY` set, if the lazy-instantiation pattern is followed for the new Gemini call the same way it already is for Trigger.dev/Liveblocks/Blob.

### Open questions

1. **Package gap**: this spec's own "all packages are already installed" claim does not hold. `@ai-sdk/google` (the Gemini provider) and `ai` (the Vercel AI SDK core package that actually issues the `generateText`/`generateObject`-style call `@ai-sdk/google` plugs into) are both genuinely absent from `package.json`. Recommendation: install both, following spec 22's own precedent of bootstrapping missing infrastructure from scratch rather than treating the spec's claim as a blocker. A further sub-question for structured output (turning Gemini's response into the seven typed actions): `ai`'s `generateObject`-style APIs conventionally take a Zod schema, but `zod` is also not installed, and spec 22's Open Questions #8 explicitly deferred adding it until a spec asks for it by name (spec 23 does not). Recommendation: use the `ai` package's own `jsonSchema()` helper (plain JSON Schema, no Zod dependency) plus this repo's existing manual-type-guard convention to validate the parsed response, keeping `zod` out of this spec's diff — a Dev-level implementation call, not a product decision.
2. **`GEMINI_API_KEY` gap**: also not present in `.env.local` despite the spec's claim (confirmed by reading the file directly). Recommendation: same posture as `TRIGGER_SECRET_KEY`/`LIVEBLOCKS_SECRET_KEY`/`BLOB_READ_WRITE_TOKEN` — a human needs to provision a real key before this task can be exercised end-to-end against a real Gemini account, and the code itself must follow the lazy-instantiation-on-first-call pattern (`lib/liveblocks.ts`/`lib/canvas-blob.ts`/`lib/trigger.ts`'s shared precedent) so `next build`'s page-data collection doesn't break with the key unset. This is a human-provisioning gap to log, not a blocker for writing the code.
3. **AI's synthetic presence identity**: `setPresence(roomId, { userId, data, userInfo, ttl })` needs a `userId` and, if the existing `LiveCursors`/`PresenceAvatars` (spec 19) rendering is to show something legible instead of a blank/anonymous entry, a `userInfo` (`name`/`avatar`/`color`). Nothing in this spec's text, `architecture-context.md`, or `ui-context.md` names a fixed AI identity. Recommendation: a fixed, constant `userId` (e.g. `"ghost-ai-agent"`, not per-run, so a stale/expired entry from a crashed run doesn't fork into a new "collaborator" each time), `name: "Ghost AI"`, and `color` sourced from `ui-context.md`'s already-reserved `--accent-ai` token (`#6457f9`) rather than the spec-10 `CURSOR_COLORS` hash palette reserved for real human participants — this keeps the AI visually distinct without inventing a new color value outside the documented palette.
4. **AI cursor position semantics**: the spec asks to "update AI presence (cursor + thinking state)," but a background task has no real pointer to track. Recommendation: set `cursor` to the position of the node most recently added/moved by the current action batch (or `null` while only "thinking," before any node exists yet), and clear it to `null` when the run finishes — a reasonable, non-literal interpretation, not a requirement pinned anywhere in the context docs. Flagging as a recommendation, not a decision made unilaterally.
5. **`ai-status-feed` payload shape**: spec 24 (not yet implemented) explicitly owns "define the feed payload schema in `types/tasks.ts`" and "validate incoming messages" with an "optional `text` field." Since `types/tasks.ts` doesn't exist yet, this spec is the first to actually broadcast onto `ai-status-feed`. Recommendation: broadcast a minimal, forward-compatible payload matching spec 24's own stated shape (an object with at least a `text: string` field) without inventing the formal schema or validation logic itself — that stays spec 24's job, not something to pull forward here.
6. **"Check Liveblocks and Trigger.dev agent skills" instruction — only partially satisfiable offline**: no Trigger.dev skill exists in this repo at all (same gap spec 22 already documented), and the Liveblocks skill's one directly relevant reference (`ai-as-a-collaborator.md`) is a link-only stub pointing to an external URL with no content fetchable in this pipeline. Recommendation: the Senior Developer should read the installed `@liveblocks/node` and `@ai-sdk/google`/`ai` packages' own `.d.ts` types directly instead (the same "read the installed SDK source, not training data" precedent spec 18 set for `@liveblocks/react-flow`'s `onDelete` and spec 22 set for `@trigger.dev/sdk`) — this brief already did exactly that to confirm `mutateStorage`/`broadcastEvent`/`setPresence`/`getStorageDocument` all exist on the installed `@liveblocks/node@^3.24.0` client and require no new package.
7. **Edge ID generation**: `lib/canvas-shapes.ts` has `generateNodeId` but no edge equivalent — every edge created so far goes through `onConnect`, a `@liveblocks/react-flow`-internal path only reachable from inside the React hook, not from server-side code. Recommendation: add a small, analogous `generateEdgeId` (or equivalent) alongside the existing node-ID recipe, used only by this spec's server-side edge-creation action — a minor, reasonable addition, not scope creep, since AI-generated edges cannot be created at all without some ID mechanism.
8. **Atomicity of the canvas write**: nothing in the spec text says whether the full set of generated actions should land as one atomic write or be applied action-by-action with visible incremental progress. Recommendation: apply the full action batch inside a single `mutateStorage` callback (mirroring spec 18's "one atomic Storage commit" precedent for template import, which was QA-forced specifically to close a transient-broken-state window other collaborators could observe) — while status (`broadcastEvent`)/presence (`setPresence`) updates, being separate ephemeral mechanisms, can still be pushed incrementally around that single write to convey progress without touching Storage more than once.
9. **"Extend" vs. "replace" semantics**: `project-overview.md`'s Core User Flow step 5 says the AI can "generate or extend the system design," and this spec's own action list (move/resize/delete existing nodes, not just add) implies the AI can operate on the current graph, not only append to it. Recommendation: actions always apply surgically against the current graph (only the specific node/edge IDs an action targets), never a wholesale clear-and-replace — nothing in this spec's text authorizes a destructive full-canvas clear the way spec 18's template import explicitly does with its own documented no-confirmation-dialog tradeoff.
10. **"Project context" as an AI input**: `architecture-context.md`'s AI Generation Model lists "user prompt, project context, and current canvas state" as inputs. Recommendation: treat "project context" as satisfied by `roomId`/`projectId` scoping alone (which room to read/write), not as a requirement to add a new Prisma read of `Project` metadata inside the trigger task — this spec's own text asks only for "prompt" as Gemini's input, and adding an unrequested Prisma dependency to `trigger/design-agent.ts` would cross a system boundary this spec doesn't ask for.

## Dev Notes

### Files added/changed

- `trigger/design-agent.ts` (rewritten) — `runDesignAgent` replaces spec 22's log-and-echo shell with the real orchestration: sets AI presence (`thinking: true`, `cursor: null`) → broadcasts `start` status → reads current room Storage (`getCurrentDesignGraph`) → broadcasts `processing` status → calls Gemini (`interpretDesignPrompt`) → sets presence `cursor` to the target position of the last `addNode`/`moveNode` action in the batch (still `thinking: true`) → applies the full batch atomically (`applyDesignAgentActions`) → broadcasts `complete` status (distinct wording for a zero-action batch) → returns `{ roomId, actionCount }`. Wrapped in `try/catch/finally`: any failure broadcasts an `error` status (itself wrapped in `.catch` so a *second* failure — e.g. Liveblocks down too — can't mask the original error) and rethrows; `finally` always clears AI presence (also `.catch`-guarded) whether the run succeeded or failed.
- `lib/design-agent-ai.ts` (new) — the Gemini/AI-interpretation module. Lazily instantiates `createGoogleGenerativeAI({ apiKey: GEMINI_API_KEY })`, cached on `globalThis` (same pattern as `lib/liveblocks.ts#getLiveblocksClient`/`lib/canvas-blob.ts`). `interpretDesignPrompt({ prompt, currentGraph })` calls `generateObject` with a `jsonSchema()`-built schema (no Zod) whose `validate` callback is this module's own manual type guard (`isValidRawAction`/`isRawDesignAgentActionsResponse`) — the actual authoritative per-kind-required-field gate, since JSON Schema alone can't express "these fields are required only when `kind` is X." A failed validation makes `generateObject` itself reject (verified via test, not assumed). Successfully-parsed raw actions are then normalized (`normalizeActions`): model-invented local node/edge IDs are replaced with real, collision-safe ones (`generateNodeId`/`generateEdgeId`), and references between actions in the same batch (e.g. an `addEdge` connecting two nodes added earlier in the same response) are resolved; an action whose reference resolves to neither the current graph nor something created earlier in the same batch is dropped, not thrown on.
- `lib/design-agent-room.ts` (new) — the Liveblocks-server-mutation/status/presence module, reusing `getLiveblocksClient()` (spec 10) exclusively — no second Liveblocks Node client anywhere. `getCurrentDesignGraph` reads current Storage via `getStorageDocument(roomId, "json")` and parses it into a plain graph summary (manual type guards, degrading a missing/malformed `"flow"` key to an empty graph rather than throwing — only genuine upstream failures propagate, mirroring `lib/canvas-blob.ts#fetchCanvasSnapshot`'s convention). `applyDesignAgentActions` applies the full batch inside **one** `@liveblocks/react-flow/node#mutateFlow` call (see Key decisions below). `broadcastDesignAgentStatus`/`setDesignAgentPresence`/`clearDesignAgentPresence` wrap `broadcastEvent`/`setPresence` with a fixed Ghost AI identity.
- `lib/canvas-shapes.ts` (modified, additive only) — added `generateEdgeId()`, mirroring `generateNodeId`'s timestamp+counter+random-suffix recipe, per Open Questions #7. `CANVAS_SHAPES`/`SHAPE_DEFAULT_SIZES`/`NODE_MIN_SIZE`/`generateNodeId`/`createDroppedNode` all confirmed untouched.
- `package.json`/`package-lock.json` — added `@ai-sdk/google@^4.0.49` and `ai@^7.0.73` (installed with `--legacy-peer-deps`, consistent with this repo's existing workaround). Both genuinely absent before this spec, confirmed via `npm ls` before installing.

### Key decisions

1. **Liveblocks-server-mutation module built on `@liveblocks/react-flow/node#mutateFlow`, not a hand-rolled `getLiveblocksClient().mutateStorage()` callback.** This is the one deliberate deviation from the brief's literal deliverables wording ("wraps `getLiveblocksClient().mutateStorage(...)`... calls"). Reading the installed `@liveblocks/react-flow@3.24.0` package directly (not guessed) showed it ships a dedicated Node-only subpath (`@liveblocks/react-flow/node`, real, documented, exported in its `package.json#exports`) whose `mutateFlow({ client, roomId }, callback)` is *itself* a thin wrapper around exactly one `client.mutateStorage(...)` call, reusing the exact same `toLiveblocksInternalNode`/`toLiveblocksInternalEdge` conversion (`LiveObject.from(node, syncConfig)`) that the client-side `useLiveblocksFlow` hook relies on for the same default `storageKey: "flow"` schema. Hand-rolling the LiveObject/LiveMap tree construction myself would have required exactly reproducing that same internal conversion logic (which fields are "atomic" vs. deep-synced, e.g. `position` is atomic but `data` is deep-synced) with no way to prove it stays in sync if the library's internals ever change. Using the package's own server-side counterpart is the more rigorous way to satisfy acceptance criterion 6's "confirmed directly against the installed types" bar. Still reuses `getLiveblocksClient()` — `mutateFlow`'s `client` option only requires an object with `.mutateStorage`, and `getLiveblocksClient()` is passed directly, so no second Liveblocks Node client is constructed anywhere. No new package was added for this — `@liveblocks/react-flow` was already a dependency (spec 11), only a different subpath of it is now imported.
2. **AI is not asked to choose node dimensions.** `SHAPE_DEFAULT_SIZES[shape]` is applied automatically to every `addNode` action; the model only supplies `shape`/`label`/`colorName`/position. This satisfies acceptance criterion 5 ("derived from `SHAPE_DEFAULT_SIZES`") by construction rather than needing post-hoc clamping/validation of an AI-chosen width/height. `resizeNode` (an action against an *existing* node) is the one action kind that does take AI-chosen dimensions, clamped to at least `NODE_MIN_SIZE` (no ceiling — nothing in the brief pins a max).
3. **AI is asked for a color *name* (`neutral`/`blue`/`purple`/.../`teal`), not a hex value or a raw `NODE_COLORS` index.** Resolved to the exact paired `{ color, textColor }` from `NODE_COLORS` by array index inside this module. This guarantees every color pair the model can produce is real and correctly paired (never an invented hex, never a fill/text mismatch) — satisfying criterion 4 by construction. The name list is a presentation-only detail kept local to `lib/design-agent-ai.ts`, not added to `types/canvas.ts`.
4. **Presence cursor semantics (Open Questions #4, a recommendation, not a pinned requirement)**: implemented literally as recommended — cursor is the target position of the most-recently-added/moved node in the generated batch (computed once, after generation, before the atomic Storage write), or `null` if the batch has neither kind of action; cleared to `null` (with `thinking: false`) once the run ends, success or failure.
5. **AI identity (Open Questions #3)**: fixed `userId: "ghost-ai-agent"`, `name: "Ghost AI"`, `color: "#6457f9"` (`--accent-ai` token). Also set `avatar: ""` (not required by `SetPresenceOptions.userInfo`, but included so `PresenceAvatars`/`LiveCursors` — spec 19's existing components, which read `other.info.avatar` as a `string` per the `UserMeta` type — never see `undefined` there; empty string cleanly falls back to Radix `Avatar`'s existing initials-fallback path).
6. **`ai-status-feed` payload (Open Questions #5)**: `{ text: string; stage: "start" | "processing" | "complete" | "error" }` — minimal and forward-compatible with spec 24's stated "object with at least a `text` field," no formal schema/validation built here (that stays spec 24's job).
7. **Atomicity (Open Questions #8)**: the full action batch is applied inside exactly one `mutateFlow`/`mutateStorage` callback. Status (`broadcastEvent`) and presence (`setPresence`) calls happen incrementally around that single write, per the brief's own recommendation, since those are separate ephemeral mechanisms.
8. **Surgical application (Open Questions #9)**: every action targets a specific node/edge ID; nothing resembling a clear-and-replace exists anywhere in this diff.
9. **"Project context" (Open Questions #10)**: no new Prisma read added to the trigger task; `roomId` scoping is the only "project context" input, per the brief's recommendation.
10. **Gemini model ID**: `"gemini-2.5-flash"`, a Dev-level pick (not pinned anywhere in the context docs) — fast/cheap and broadly available, reasonable for a bounded structured-output task like this one.
