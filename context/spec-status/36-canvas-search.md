Source spec: `context/feature-specs/36-canvas-search.md`

## Analyst Brief

### Scope statement

Add a toolbar-triggered search control to the canvas that lets a user find a node by label (case-insensitive substring match, live-filtered as they type) and jump the viewport to it, with a brief visual highlight on arrival. Current-canvas-only, node-labels-only, button-triggered-only — no multi-project search, no edge search, no keyboard shortcut.

### Concrete deliverables

- `components/ui/popover.tsx` (new) — added via `npx shadcn add popover`, **not** hand-written. This repo's actual mechanism for adding a new shadcn primitive is the CLI, confirmed by `progress-tracker.md`'s own precedent for `avatar.tsx` ("new, via `npx shadcn add avatar`, not hand-written," spec 19) and by `components.json`'s `"style": "base-nova"` preset — every existing generated primitive (`dialog.tsx`, `tabs.tsx`, `avatar.tsx`) is built on `@base-ui/react` primitives under that preset, not raw Radix, even though several `@radix-ui/*` packages remain in `package.json` as pre-existing dependencies. Running the CLI (rather than hand-authoring a Popover against `@base-ui/react/popover` directly) keeps this new primitive consistent with that same generated pattern instead of introducing a one-off. Confirmed via `Glob` on `components/ui/*.tsx` that no `popover.tsx` (or `command.tsx`) exists yet. This is a protected foundation component per `ai-workflow-rules.md` once added — used, not redesigned.
  - **Popover, not Command**: the raw spec text literally names "a shadcn `Popover` component" as what to add (the phrase "command list" in the same sentence describes the *interaction pattern* — a filtered list under a text input — not a request for shadcn's `Command`/`cmdk`-backed component). No `cmdk` dependency exists anywhere in `package.json` today, and nothing about this feature (≤20 plain-text results, no fuzzy scoring, no grouping, no arrow-key navigation asked for) needs `Command`'s heavier machinery over a plain `Input` inside `PopoverContent`. See Open Questions below for the one place this is still a judgment call.
- `hooks/use-canvas-search-highlight.ts` (new) — a small `React.createContext<string | null>(null)` (`CanvasSearchHighlightContext`) plus a thin `useCanvasSearchHighlight()` hook, structurally identical to the existing `hooks/use-update-canvas-node.ts`/`hooks/use-update-canvas-edge.ts` pair (context provided by `CanvasFlow`, consumed by the leaf `CanvasNode` renderer) — per `architecture-context.md`'s Hooks Convention ("new client-side hooks go in a top-level `hooks/` folder"). Value is the currently-highlighted node's `id`, or `null`. Deliberately **not** Liveblocks Presence or Storage — this is a private, ephemeral navigation aid for the searching user only, not collaborative canvas content, and the spec's own Scope Limit ("do not modify `canvas-node.tsx`'s drag/edit/select behavior beyond the temporary highlight") rules out routing it through the same synced `onNodesChange`/`data` path node labels/colors use.
- `components/editor/canvas-search-popover.tsx` (new) — the self-contained search control: a `PopoverTrigger` styled as an icon button (`Search` icon from `lucide-react`, same `variant="ghost" size="icon-lg"` as every other `CanvasControlBar` button) and `PopoverContent` holding an `Input` (reusing the existing `components/ui/input.tsx`) plus the live-filtered result list (plain buttons/list items, not `Command`). Owns its own local `query: string` and open/closed state (`Popover`'s own controlled or uncontrolled `open` state — component-local `useState`, since nothing outside this component needs to read the current search text or open state). Computes matches via a `useMemo` over its `nodes` prop:
  - Filter: case-insensitive substring match of `query` against each node's `data.label` (skip nodes with an empty/untitled label when `query` is non-empty, since an empty string always "matches" a substring search and would flood results with every untitled node).
  - Order: primarily by earliest match index (`label.toLowerCase().indexOf(query.toLowerCase())`, ascending), secondarily by `label` (string comparison) when match positions tie.
  - Cap: `.slice(0, 20)` — a `SEARCH_RESULTS_LIMIT = 20` constant, per the spec's own literal number.
  - Empty query (`query.trim() === ""`): renders no results (see Open Questions #4) rather than the unfiltered full node list.
  Receives `nodes: CanvasNode[]` and `onSelectNode: (node: CanvasNode) => void` as plain props (threaded from `CanvasFlow`, the only place the room's live `nodes` exists — same "handler/data down, dumb child renders" convention every other `CanvasControlBar` button already follows). Selecting a result calls `onSelectNode(node)`, then closes the popover and clears `query`.
- `components/editor/canvas-control-bar.tsx` (modified) — two new props, `nodes: CanvasNode[]` and `onJumpToNode: (node: CanvasNode) => void`, and a **fifth** button group: another `bg-surface-border` divider (matching the existing 1px-divider convention) followed by `<CanvasSearchPopover nodes={nodes} onSelectNode={onJumpToNode} />`, appended **after** the existing Save-as-template group — per the spec's own Notes ("add this as its own group rather than mixing it into an existing one") and this file's own established precedent of every new capability appending its own trailing group (export-as-image, then save-as-template, now search) rather than inserting into the middle of the bar. `CanvasControlBar` itself stays a thin composer — it does not own the query/filter/open state, only renders/wires the self-contained popover component, the same split already used for `SaveTemplateDialog`/`StarterTemplatesModal` (owned/rendered by `CanvasFlow`, `CanvasControlBar` only gets a trigger prop) adapted for a same-position-anchored popover instead of a centered modal.
- `components/editor/canvas.tsx` (modified) — `CanvasFlow` gains:
  - `handleJumpToNode(node: CanvasNodeAlias)`: computes the target node's center via `getNodesBounds([node])` — the exact same `@xyflow/react` utility `handleExportImage` already imports and calls (on the full `nodes` array, for the whole-diagram bounding box); called here with a single-element array to get that one node's own `{ x, y, width, height }` box, then `center = { x: bounds.x + bounds.width / 2, y: bounds.y + bounds.height / 2 }` — not a hand-rolled `node.position.x + (node.width ?? 0) / 2` calculation, which would need its own fallback for a node with no `width`/`height` yet. Calls `setCenter(center.x, center.y, { zoom: SEARCH_JUMP_ZOOM, duration: ZOOM_TRANSITION_DURATION_MS })` — `setCenter` comes from the same `useReactFlow()` call already destructured in this file for `screenToFlowPosition`/`zoomIn`/`zoomOut`/`fitView`; `ZOOM_TRANSITION_DURATION_MS` (the existing 200ms constant) is reused as-is rather than inventing a second duration constant; `SEARCH_JUMP_ZOOM` is new — see Open Questions #1.
  - Sets `highlightedNodeId` state to the target node's `id`, and (via a `useRef`-tracked timeout — clearing any previously-pending timeout first, so two rapid searches in a row don't leave a stale clear firing late or two nodes highlighted at once) schedules it back to `null` after `SEARCH_HIGHLIGHT_DURATION_MS = 1500` — the spec's own literal "~1.5s."
  - Renders a new `<CanvasSearchHighlightContext.Provider value={highlightedNodeId}>`, nested alongside the existing `CanvasNodeUpdateContext.Provider`/`CanvasEdgeUpdateContext.Provider` wrapping.
  - Passes `nodes` (already destructured from `useLiveblocksFlow`) and `handleJumpToNode` down to `<CanvasControlBar>` as its new `nodes`/`onJumpToNode` props.
  No `Canvas`/`CanvasProps`-level change — unlike most recent specs, this feature's state never needs to leave the room-bounded `CanvasFlow` subtree (no push-up to `WorkspaceShell`), since nothing outside the canvas needs to know about search/highlight state.
- `components/editor/canvas-node.tsx` (modified, minimal) — calls `useCanvasSearchHighlight()`, compares the returned id to its own `id` prop, and conditionally adds a highlight class/style to the **existing** `group relative` outer wrapper `<div>` (the same element that already wraps `ShapeVisual` and the four connection handles) via `cn(...)` — not a new element, and not applied inside `ShapeVisual` itself. Per the spec's explicit Scope Limit, this is the *only* change permitted in this file; drag/resize/edit/select/handle behavior is untouched. See Open Questions #2 for the exact visual treatment.

### Acceptance criteria

1. A search icon button exists in `CanvasControlBar`, in its own group separated by the same `bg-surface-border` divider convention already used between the bar's other groups.
2. Clicking the button opens a shadcn `Popover` (`components/ui/popover.tsx`, added via `npx shadcn add popover`) containing a text input — not the shadcn `Command` component, and not a hand-written popup.
3. Typing in the input live-filters the canvas's current `nodes` (the same array `CanvasFlow` already holds via `useLiveblocksFlow`) by case-insensitive substring match against each node's `data.label`.
4. Results are capped at 20, ordered by earliest match position first, then by label for ties.
5. Selecting a result calls `useReactFlow().setCenter()` with that node's real center, computed via `getNodesBounds([node])` — the same bounds-computation utility `handleExportImage` already uses, not a separately hand-rolled calculation — and then closes the popover.
6. Selecting a result also triggers a temporary highlight on the target node, applied in `canvas-node.tsx`, cleared after ~1.5 seconds; rapid consecutive selections never leave two nodes highlighted at once or a highlight that never clears.
7. The highlight is local, ephemeral React state (a new context provided by `CanvasFlow`) — never written to Liveblocks Storage or Presence, and never visible to other collaborators.
8. `canvas-node.tsx`'s existing drag, resize, label-edit, select, and connection-handle behavior is unmodified — the only diff in that file is the conditional highlight class/style.
9. No edge search exists anywhere in this diff.
10. No cross-project/cross-room search exists — matching is scoped to the current room's live `nodes` only.
11. No keyboard shortcut (e.g. Cmd/Ctrl+K) opens the search popover — a toolbar button is the only entry point.
12. `npm run build` (and this repo's standard mechanical gate — `npx tsc --noEmit`, `npx eslint`, `npx vitest run --no-file-parallelism`) all pass.

### Open questions

1. **Exact zoom level to jump to.** The spec's own text only says `setCenter(x, y, { zoom, duration })` without pinning a number for `zoom`.
   **Recommendation:** a new `SEARCH_JUMP_ZOOM = 1` constant (the diagram's authored 1:1 scale) — the same reference scale `handleExportImage` already treats as meaningful ("exports at the diagram's authored 1:1 scale... not whatever zoom the viewer happens to be at"). This is a Dev-level, spec-silent value in the same category as `ZOOM_TRANSITION_DURATION_MS`/`NODE_MIN_SIZE` — any reasonable fixed value satisfies every acceptance criterion above, since none of them name an exact number.

2. **Exact highlight visual treatment.** The spec says "a short-lived CSS class or inline style toggle... briefly highlight the target node," without specifying what it should look like.
   **Recommendation:** a `ring`/box-shadow glow on the node's outer wrapper `<div>` using the existing `--accent-primary`/`border-brand` token (not a new color), but rendered distinctly from the existing `selected`-state border treatment (e.g. a wider or offset ring) so a search-jump stays visually obvious even when the jumped-to node also happens to be currently selected. Exact Tailwind utility/values are a Dev-level styling call within `ui-context.md`'s existing token constraints (no raw hex, no new color).

3. **Whether the popover's trigger+content should be a standalone component or inlined into `canvas-control-bar.tsx`.** The spec's text doesn't address file structure.
   **Recommendation:** the dedicated `canvas-search-popover.tsx` file described in Concrete deliverables above — keeps `CanvasControlBar` a thin composer (matching its existing role for every other button/group) and keeps the query/filter/sort logic isolated and independently testable, the same separation this codebase already uses for `SaveTemplateDialog`/`StarterTemplatesModal` relative to `CanvasControlBar`/`CanvasFlow`. Not a hard requirement — inlining into `canvas-control-bar.tsx` directly would also satisfy every acceptance criterion above, but the Senior Developer shouldn't have to independently re-derive this split.

4. **What renders when the query is empty (nothing typed yet).** The spec says results are "live-filtered... as the user types," but doesn't say what an empty query should show.
   **Recommendation:** render no results (or a plain "Type to search nodes" placeholder state) rather than the full unfiltered node list — avoids an unbounded list on open for a large diagram and avoids a state where "ordered by match position" has no real match position to order by. Not a hard requirement — showing the first 20 nodes in some other order for an empty query wouldn't violate any acceptance criterion above, but would be a materially different (and, per this recommendation, less useful) empty state.

### Out-of-scope callouts

- **Search across multiple projects** — explicit Scope Limit in the raw spec text; matching is scoped to the current room's live `nodes` only.
- **Edge search** — explicit Scope Limit; nodes only, no `data.label` matching against `CanvasEdgeData`.
- **Keyboard-shortcut activation (e.g. Cmd/Ctrl+K)** — explicit Scope Limit for this spec; a toolbar button is the only entry point. (`hooks/use-keyboard-shortcuts.ts` is not touched by this diff.)
- **Any change to `canvas-node.tsx`'s drag/edit/select/resize/connection-handle behavior beyond the temporary highlight** — explicit Scope Limit; the highlight is additive only.

Kept as local React state/context only (see Concrete deliverables and Acceptance Criterion 7).

- **shadcn `Command`/`cmdk`** — the raw spec names `Popover` specifically; no `cmdk` dependency exists in this codebase, and nothing about a ≤20-result plain substring search needs it (see Concrete deliverables' "Popover, not Command" note).
