Source spec: `context/feature-specs/33-custom-templates.md`

## Analyst Brief

### Scope statement

Let a signed-in user save their current canvas as a private, named `CustomTemplate` (Postgres metadata + Blob-stored node/edge JSON, mirroring the `ProjectSpec`/`lib/spec-blob.ts` pattern), list and delete their own saved templates, and import a saved template back into the canvas through spec 18's existing clear-then-add replace flow unchanged. Nothing else — no sharing, no editing an existing saved template, no change to the built-in `CANVAS_TEMPLATES` library or its preview rendering, and no change to the export-as-image logic already in `components/editor/canvas.tsx`.

### Concrete deliverables

- `prisma/schema.prisma` (modified) — new `CustomTemplate` model: `id` (`@id @default(cuid())`, matching every other model's ID convention), `ownerId` (`String`, Clerk user ID — no relation to `Project`, per the spec's own "not project-scoped" note), `name` (`String`, required), `description` (`String?`, optional — matches `Project.description`'s nullable convention), `filePath` (`String`, required — the Blob URL, matching `ProjectSpec.filePath`), `createdAt` (`DateTime @default(now())`). A real migration created and applied (`prisma migrate dev`), matching spec 28's precedent. See Open Questions #1–#2 for the exact index and field-constraint recommendation.
- `lib/template-blob.ts` (new) — mirrors `lib/canvas-blob.ts`/`lib/spec-blob.ts`'s exact shape: lazy `requireBlobToken()`, `TEMPLATE_BLOB_ACCESS = "private"`, `templateBlobPathname(ownerId, templateId)` returning `templates/{ownerId}/{templateId}.json`, `uploadTemplateJson(ownerId, templateId, snapshot)` (`put`, `allowOverwrite: true`, `addRandomSuffix: false`, same as the other two), `fetchTemplateJson(blobUrl)` (`get`, returns `null` for "nothing there" vs. throwing for a genuine upstream failure, same distinction `fetchCanvasSnapshot`/`fetchSpecMarkdown` already make). Additionally needs a new `deleteTemplateJson(blobUrl)` using `@vercel/blob`'s `del(url, { token })` — genuinely new territory in this codebase (grepped: no `del` call exists anywhere yet; `canvas-blob.ts`/`spec-blob.ts` are upload+fetch only since neither canvas snapshots nor generated specs are ever deleted). A failed Blob delete should not silently succeed — see Open Questions #4 for the delete-ordering recommendation.
- `app/api/templates/route.ts` (new) — `GET`: `getCallerIdentity()` (401 if absent, no `getProjectAccess` call — not project-scoped) → `prisma.customTemplate.findMany({ where: { ownerId }, orderBy: { createdAt: "desc" } })` → metadata-only response (`{ templates: [{ id, name, description, createdAt }] }`, never `filePath`, mirroring `GET /api/projects/[projectId]/specs`'s existing metadata-only convention). `POST`: `getCallerIdentity()` → parse+validate body with Zod (`{ name, description?, nodes, edges }`) → `uploadTemplateJson` → `prisma.customTemplate.create` → `{ template: { id, name, description, createdAt } }`. Follows `app/api/projects/[projectId]/specs/route.ts` (spec 28) and `app/api/ai/design/route.ts`'s failure-precedence convention: 401 → 400 (Zod) → 500 (Blob/Prisma failure).
- `app/api/templates/[templateId]/route.ts` (new) — `GET` and `DELETE`, both: `getCallerIdentity()` (401) → `prisma.customTemplate.findUnique` → missing row → 404 → `template.ownerId !== identity.userId` → 403 (the exact 404-then-403 precedence `lib/projects.ts#getOwnedProjectOrError` already establishes for owner-only routes — not a new pattern). `GET` additionally fetches the Blob content via `fetchTemplateJson` and returns the full importable shape (`{ id, name, description, nodes, edges }`, matching `CanvasTemplate`'s own field set exactly so the modal can hand the response straight to `onImport` with no reshaping). `DELETE` calls `deleteTemplateJson` then `prisma.customTemplate.delete`, returning `{ success: true }`.
- `components/editor/canvas-control-bar.tsx` (modified) — a new "Save as template" icon button in the existing pill, after another `bg-surface-border` divider (same convention the Export-as-image button already uses). Per Open Questions #3, the recommended shape is a plain new `onOpenSaveTemplate: () => void` prop (a trigger only) — the dialog's own JSX/state is expected to live elsewhere (see below), keeping `CanvasControlBar` consistent with its own documented "plain props, no local complex state" convention.
- `components/editor/canvas.tsx` (modified — **not listed in the task's own "It touches" summary, but a small additive change here is unavoidable**; see Open Questions #3) — `CanvasFlow` already holds the room's live `nodes`/`edges` locally (the same values `handleExportImage`/`handleImportTemplate`/the `onCanvasGraphChange` effect already read). A new `SaveTemplateDialog` component (new file, or inline — Dev's call) is rendered as a sibling of the existing `<StarterTemplatesModal>`, wired through new `isSaveTemplateDialogOpen` state and a `handleSaveTemplate(name, description)` callback that POSTs `{ name, description, nodes, edges }` using `CanvasFlow`'s own current `nodes`/`edges`. `CanvasControlBar` only receives the new `onOpenSaveTemplate` trigger prop, mirroring exactly how `isTemplatesModalOpen`/the Templates navbar button already separate "the button that opens it" from "the dialog that owns the mechanism." This spec's own explicit Scope Limit ("do not touch `canvas.tsx`'s export-as-image logic") only carves out that one piece of logic — it would be redundant if all `canvas.tsx` edits were forbidden, so this reading is well-supported, not invented.
- `components/editor/starter-templates-modal.tsx` (modified) — a new "My Templates" section (its own labeled grid, alongside but visually distinct from the existing `CANVAS_TEMPLATES` grid — the raw spec doesn't specify exact placement/heading text, a Dev-level layout choice within the existing card-grid convention). Calls `useCustomTemplates()` directly inside this component (mirroring `SpecsTab`'s existing precedent of calling `useProjectSpecs` directly in a leaf component rather than lifting fetch state to `WorkspaceShell`/`CanvasFlow` — `ShareDialog`'s "fully presentational, state owned by parent" convention is the *other* precedent in this codebase, but `SpecsTab`'s is the closer match since both are read from inside a spec 18/20-style modal/tab that already owns no other cross-cutting state). Each "My Templates" card gets a delete button (same `removingId`-tracked busy-state convention `ShareDialog`'s collaborator removal already uses) in addition to the existing Import button pattern. This brief does not characterize what that existing diff contains.
- `hooks/use-custom-templates.ts` (new) — `useCustomTemplates()`: fetch-and-`useState` shape mirroring `hooks/use-project-specs.ts` (`{ templates, isLoading, error, refetch }`, no `projectId` argument since this isn't project-scoped), plus a `remove(templateId)` mutation mirroring `hooks/use-collaborators.ts`'s `remove()` (tracks its own `removingId`, calls `DELETE /api/templates/[templateId]`, optimistically filters the deleted row out of local state on success). The raw spec names `use-project-specs.ts` as the mirror target for the list/fetch shape only — the delete capability is this brief's own well-supported addition, since the spec explicitly requires "Add a delete action per saved template card" and that action has to live somewhere with access to the list state it mutates.

### Acceptance criteria

1. `CustomTemplate` exists in `prisma/schema.prisma` with `id`, `ownerId`, `name`, `description` (nullable), `filePath`, `createdAt`, and a real, applied migration — no `projectId` field anywhere on the model.
2. `POST /api/templates` requires authentication (401 if not signed in), validates `{ name, description?, nodes, edges }` with Zod (400 on failure), uploads the node/edge JSON to `templates/{ownerId}/{templateId}.json` via Blob, and creates a `CustomTemplate` row scoped to the caller's own `ownerId`.
3. `GET /api/templates` requires authentication and returns only the caller's own templates (metadata only — never `filePath`/the raw Blob URL).
4. `GET /api/templates/[templateId]` and `DELETE /api/templates/[templateId]` both require authentication and both reject a caller who isn't the template's `ownerId` (403 for an existing-but-not-owned template, 404 for a nonexistent one) — no cross-user access in either direction.
5. `DELETE /api/templates/[templateId]` removes both the Prisma row and the underlying Blob object — a deleted template's content is not retrievable afterward.
6. A user can open a "Save as template" flow from the canvas control bar, enter a name (and optional description), and save the canvas's current live nodes/edges as a new `CustomTemplate` without leaving the editor.
7. Saved templates appear in a "My Templates" section of the starter templates modal, visible only to the user who saved them (verified via the owner-only API gate, not just client-side filtering).
8. Importing a saved template clears the existing canvas and loads the saved template's nodes/edges through the exact same mechanism spec 18 built for built-in templates (`handleImportTemplate`'s `room.batch(onDelete + onNodesChange + onEdgesChange)` + `fitView`) — no second, parallel import code path.
9. Deleting a saved template removes it from the "My Templates" list immediately (no manual refresh needed) and from Blob storage.
10. The built-in `CANVAS_TEMPLATES` array, `starter-templates.ts`, and the SVG preview mechanism in `starter-template-preview.tsx` are untouched.
11. `components/editor/canvas.tsx`'s `handleExportImage` and the Export-as-image button/behavior are untouched.
12. No sharing of a saved template with another user, and no "edit an existing saved template" flow (delete-and-re-save only) exist anywhere in this diff.
13. `npm run build` (and this repo's established mechanical gate — `npx tsc --noEmit`, `npx eslint`, `npx vitest run --no-file-parallelism`, `npx next build`) all pass.

### Open questions

1. **Exact Prisma field types/constraints, and whether `ownerId` should be indexed.** The raw spec text lists only field names (`id, ownerId, name, description, filePath, createdAt`), not types, nullability, or indexes.
   **Recommendation:** `name: String` (required — a save action should not silently produce an unnamed row the way `Project`'s create-with-default-name convention does; see Open Questions #3), `description: String?` (optional, matching `Project.description`'s existing nullable pattern), `filePath: String` (required, matching `ProjectSpec.filePath`). For the index: yes, index `ownerId` — every real query against this table filters by it (`GET /api/templates`'s list, both `[templateId]` routes' ownership check reads the row by `id` first but the *list* route is the hot path). Recommend a composite `@@index([ownerId, createdAt])`, mirroring `ProjectSpec`'s own `@@index([projectId, createdAt])` — the directly analogous "list rows scoped to X, sorted by createdAt" query shape — rather than `Project`'s two-separate-single-column-index style, since this table has no other query pattern that would benefit from `ownerId` and `createdAt` being independently indexable.

2. **Whether node/edge JSON should be validated with Zod before upload, and how strictly.** The raw spec explicitly says "validate with Zod" for `POST /api/templates`'s body — unlike the precedent `PUT /api/projects/[projectId]/canvas` route (`app/api/projects/[projectId]/canvas/route.ts`), which only does a shallow `Array.isArray(body.nodes) && Array.isArray(body.edges)` check with no Zod involved and no per-node/per-edge shape validation at all. Spec 27's existing Zod node/edge schemas (`GenerateSpecGraphNodeSchema`/`GenerateSpecGraphEdgeSchema` in `trigger/generate-spec.ts`) are the only Zod-validated node/edge precedent in the codebase, but they're a deliberately narrow *structural summary* (`{ id, label, shape, x, y }`) for spec-generation prompt input — reusing them here would silently drop `color`/`textColor`/`width`/`height`, breaking faithful re-import (a re-imported template would lose its saved colors and sizing).
   **Recommendation:** author new, dedicated Zod schemas in `app/api/templates/route.ts` (or a shared `lib/template-schema.ts` if Dev prefers reuse between the POST route and any future validation need) that validate full re-import fidelity: node `{ id: string, type: string, position: { x: number, y: number }, width: number.optional(), height: number.optional(), data: { label: string, color: string, textColor: string, shape: z.enum([...NODE_SHAPES]) } }`, edge `{ id: string, type: string, source: string, target: string, data: { label: string.optional() } }`. Use plain `z.object(...)` (Zod's own default already strips unrecognized keys rather than erroring) — not `.strict()` — since a live React Flow node object may carry additional runtime-only fields (e.g. `selected`, `measured`) that aren't essential to re-import and shouldn't fail an otherwise-valid save.

3. **Where does the "Save as template" dialog's own JSX/state live — inside `canvas-control-bar.tsx` itself, or lifted to `canvas.tsx`?** The raw spec's phrasing ("Add a 'Save as template' action to `canvas-control-bar.tsx`... It opens a small save dialog") most literally reads as putting the whole dialog inside that file, and the task's own "It touches" list names `canvas-control-bar.tsx` but not `canvas.tsx`. But `CanvasControlBar` is documented (`ui-context.md`'s Canvas Control Bar section, and its own file's docblock) as a deliberately thin, props-only, no-local-complex-state component — every one of its existing actions (zoom, undo/redo, export) is a plain callback prop, with the *mechanism* (React Flow instance calls, Liveblocks history hooks, the `toPng` export pipeline) living in `CanvasFlow`. Spec 18 established the parallel precedent for a full dialog: the "Templates" *button* lives in `workspace-navbar.tsx`, but the `StarterTemplatesModal` dialog itself is rendered by `CanvasFlow`, which is also the component that already holds the live `nodes`/`edges` this save flow needs.
   **Recommendation:** keep `CanvasControlBar` unchanged in kind (a new button + a plain `onOpenSaveTemplate: () => void` trigger prop only), and render the actual `SaveTemplateDialog` (new component) as a sibling of `<StarterTemplatesModal>` inside `CanvasFlow`, which owns the open/close state and the `POST /api/templates` call using its own already-in-scope `nodes`/`edges`. This satisfies "add a save-as-template action to `canvas-control-bar.tsx`" (the button/action does live there) without breaking that component's established thin-and-presentational convention, and avoids threading raw `nodes`/`edges` arrays down as new `CanvasControlBar` props (which would otherwise be the only alternative). This is the one place this brief deviates from the most literal reading of the raw spec text's file placement — Senior Developer should treat it as this brief's best-supported recommendation, not an already-settled decision, and record whichever way it lands in Dev Notes.

4. **Delete ordering: Blob-first or Prisma-first, and what happens on a partial failure?** The raw spec just says "Deleting a saved template removes it from the list and from Blob storage" — it doesn't specify ordering or how to handle one succeeding and the other failing. No existing precedent in this codebase deletes *both* a Prisma row and its paired Blob object (canvas snapshots and specs are never deleted; `ProjectCollaborator`/`Project` deletes cascade in Postgres only, no paired Blob content).
   **Recommendation:** delete the Prisma row first, then best-effort delete the Blob object (matching spec 28's `persistGeneratedSpec`'s own precedent of treating "the row is the source of truth, a stray Blob object is an acceptable, non-fatal leftover" — that helper deletes a *placeholder row* best-effort on a later failure, the same "don't let a secondary cleanup failure block or corrupt the primary operation" posture). Concretely: `prisma.customTemplate.delete(...)` first (so the template disappears from the owner's list immediately and can never be re-fetched via `GET /api/templates/[templateId]` even if the Blob delete below fails), then `deleteTemplateJson(...)` in a try/catch that logs but does not fail the request on error — an orphaned Blob object with no reachable Prisma row is a harmless, low-stakes leftover (private store, never listed or served to any client), not a correctness bug, given this app has no storage-quota/billing concern (`project-overview.md`'s Out of Scope wall excludes billing entirely).

5. **Save-dialog validation rules for `name`/`description`.** The raw spec only says "name + optional description" with no length limits or other constraints, and no other model/dialog in this codebase enforces a max length anywhere (confirmed: `POST /api/projects` has no length check either).
   **Recommendation:** `name` required, trimmed, non-empty (Zod `.trim().min(1)`); the dialog's own Save button disabled while the trimmed name is empty, mirroring `ShareDialog`'s exact `disabled={!email.trim() || isInviting}` pattern for its own required-field submit button. `description` optional, trimmed, no minimum. No maximum length on either field — inventing an arbitrary cap (e.g. 100 characters) isn't supported by anything in the spec text or an existing precedent, so it's left unconstrained rather than guessed at.

- **Delete ordering (Open Questions #4)**: Prisma row deleted first, then a best-effort, logged-not-thrown Blob delete — verified by a dedicated test asserting call order (`prisma-delete` before `blob-delete`) and a second test confirming the route still returns `{ success: true }` when the Blob delete itself fails.
- **Save-dialog validation (Open Questions #5)**: `name` required/trimmed/non-empty (both client-side disabled-button and server-side Zod `.trim().min(1)`), `description` optional/trimmed, no max length on either — matches the brief's recommendation and the "no precedent for a max length anywhere in this codebase" finding.
- **POST /api/templates persistence pattern**: used the two-write placeholder-row pattern (create → upload → update, with best-effort placeholder cleanup on failure) rather than a literal "upload then create" — necessary because `templateBlobPathname` needs a `CustomTemplate.id`, and Prisma's `@default(cuid())` only generates one at insert time. This is the same constraint and the same resolution spec 28's `persistGeneratedSpec` already established, and the brief's own Open Questions #4 explicitly cites that helper as the precedent to follow.
- **"My Templates" fetch timing**: `useCustomTemplates()` fetches on mount inside `StarterTemplatesModal`, unconditionally (not gated by the dialog's own `open` prop) — mirrors `SpecsTab`'s existing precedent of `useProjectSpecs` auto-fetching on mount regardless of which AI-sidebar tab is active. `canvas.test.tsx` mocks this hook (the same "verify wiring, not the child hook's own internals" convention already applied to `useCanvasAutosave`/`useAiStatusFeed`/`useAiChatFeed` in that file) so this file's shared `fetchMock` isn't polluted by an unrelated `GET /api/templates` call on every `Canvas` mount.
