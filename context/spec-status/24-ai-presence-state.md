Source spec: `context/feature-specs/24-ai-presence-state.md`

## Analyst Brief

### Scope statement

Wire the already-shipped AI Sidebar and live cursors (specs 19/20) up to spec 23's already-broadcasting `ai-status-feed` and AI presence (`thinking`/`cursor`) so every connected participant — not just whoever eventually submits a prompt — can see a small "AI is working" status in the sidebar, a disabled/loading chat input while a run is active, and a thinking spinner on the Ghost AI cursor badge. This unit is UI/presence/realtime-signal plumbing only: it defines and validates the feed's payload schema in `types/tasks.ts` and consumes what spec 23 already produces — it does not add the actual submit-a-prompt-and-trigger-generation flow (spec 26) or the persisted chat feed (spec 25).

### Concrete deliverables

- `types/tasks.ts` (new — does not exist yet) — the formal, code-level schema this spec's own text names as its deliverable: an `AiStatusStage` union (`"start" | "processing" | "complete" | "error"`, matching spec 23's already-shipped `DesignAgentStatusStage` in `lib/design-agent-room.ts` exactly, not a redefinition with different values) and an `AiStatusMessage` interface with a required `stage: AiStatusStage` and an **optional** `text?: string` (per the spec's own "the payload should support an optional `text` field" — spec 23's actual broadcasts always happen to include `text`, which is a valid subtype of "optional," so no producer change is required for correctness; see Open Questions #2 for whether `lib/design-agent-room.ts` should import this file's types instead of keeping its own duplicate). Also exports a runtime type guard (`isAiStatusMessage`, manual — no Zod, matching spec 23's precedent of skipping Zod for this exact feed) used to validate an incoming `ai-status-feed` broadcast before it touches any UI state.
- `hooks/use-ai-status-feed.ts` (new — per `architecture-context.md`'s Hooks Convention, new client hooks go in `hooks/`) — wraps Liveblocks' `useEventListener` (`@liveblocks/react/suspense`) subscribed to `"ai-status-feed"`, validates each incoming event via `isAiStatusMessage`, and keeps only the latest valid message in local state (discarding anything that fails validation, per this spec's "validate incoming messages before displaying them"). Must be called from a component already inside the room's `RoomProvider` boundary — see Open Questions #1 for where that is.
- `components/editor/canvas.tsx` (modified) — `CanvasFlow` (already inside `RoomProvider`, per its existing `onSaveStatusChange` precedent from spec 21) calls the new hook and pushes the latest validated status message up to `WorkspaceShell` via a new `onAiStatusChange` callback prop, mirroring `onSaveStatusChange`'s existing "room-scoped value pushed up via callback, not a new context" convention exactly.
- `components/editor/workspace-shell.tsx` (modified) — owns a new `aiStatus: AiStatusMessage | null` state (mirrors `saveStatus`), wires `onAiStatusChange={setAiStatus}` into `<Canvas>`, and threads `aiStatus` down to `<AiSidebar>` as a new prop.
- `components/editor/ai-sidebar.tsx` (modified) — forwards the new `aiStatus` prop straight through to `<AiArchitectTab>` (same "pass the real mechanism down as props" posture spec 18/21 already established) — no new state owned here.
- `components/editor/ai-architect-tab.tsx` (modified) — the actual UI changes this spec's text asks for, all scoped to this one component:
  - a small, non-blocking status line (icon + `aiStatus.text`, styled with the sidebar's existing `--accent-ai`/`text-ai-text` token — matching the Bot icon/header/Send button's existing visual language, not a new color), visible only while `aiStatus.stage` is `"start"` or `"processing"` ("when AI is working"); renders nothing before the first message of the session arrives or once a run reaches `"complete"`/`"error"`, mirroring `SaveStatusIndicator`'s existing "nothing for idle" convention (spec 21) rather than inventing a new visibility rule.
  - the `Textarea` and Send `Button` gain a `disabled` condition of `aiStatus?.stage === "start" || aiStatus?.stage === "processing"`, in addition to the existing empty-input `disabled` check.
  - the Send button swaps its `Send` icon for a spinner (`Loader2` + `animate-spin`, the same spin convention `SaveStatusIndicator`/`share-dialog.tsx` already use) while that same active-generation condition is true.
  - tab switching, the Specs tab, and the sidebar's close button are untouched — nothing here dims or blocks the rest of the sidebar (this spec's own explicit Scope Limit).
- `components/editor/live-cursors.tsx` (modified) — `CursorPresence`'s `useOther` selector gains a `thinking: boolean` field (reading `candidate.presence.thinking`, the pinned `Presence.thinking` field from `liveblocks.config.ts`); `LiveCursor` renders a small spinner (`Loader2`/`animate-spin`, sized to fit inside the existing name-badge pill, e.g. `h-3 w-3`) next to the name when `other.thinking` is `true`, nothing when `false` or absent. No change to the existing null-cursor early return — see Open Questions #3 for why this means the spinner won't always be visible while Ghost AI is "thinking."
- Tests: `types/tasks.test.ts` (new — schema shape, `isAiStatusMessage` accept/reject cases including a message with `text` omitted and one with an invalid `stage`), `hooks/use-ai-status-feed.test.ts` (new — subscribes correctly, keeps only the latest valid message, drops an invalid one), `components/editor/ai-architect-tab.test.tsx` (extended — status line visibility per stage, input/button disabled state, spinner-vs-icon on the Send button), `components/editor/live-cursors.test.tsx` (extended — spinner shown/hidden per `thinking`), `components/editor/canvas.test.tsx` and `components/editor/workspace-shell.test.tsx` and `components/editor/ai-sidebar.test.tsx` (extended — new prop threading).
- No changes to `trigger/design-agent.ts`, `lib/design-agent-ai.ts`, `app/api/ai/design*`, or the `TaskRun` model — spec 23's territory, already delivered; this spec only consumes what it already broadcasts (aside from the possible `lib/design-agent-room.ts` type-alignment noted in Open Questions #2, which touches only type imports, not producer logic).

### Acceptance criteria

1. `types/tasks.ts` exists and exports an `AiStatusStage` union with exactly the four values `"start" | "processing" | "complete" | "error"` and an `AiStatusMessage` type with a required `stage` and an optional `text: string`.
2. A runtime validator (`isAiStatusMessage` or equivalent) rejects a malformed/foreign payload (wrong `stage` value, missing `stage`, non-string `text`) — a bad broadcast on the same room does not reach or corrupt UI state.
3. The AI Sidebar subscribes to `ai-status-feed` via Liveblocks' real `useEventListener` mechanism (not polling, not a second websocket, not a parallel realtime system) and reflects the **latest** message only — no list/history of past status messages renders anywhere.
4. The status reflected in the sidebar is visible to **every** participant connected to the room while a run is active, not only the participant who triggered it — since it comes from a room-broadcast `broadcastEvent`, not local-only state.
5. The chat `Textarea` and Send button in the AI Architect tab are disabled while the latest status's `stage` is `"start"` or `"processing"`, and re-enabled once it reaches `"complete"` or `"error"` (subject to the existing empty-input disabled rule).
6. The Send button shows a loading/spinner state while that same active-generation condition is true.
7. No other part of the sidebar (tab switching, Specs tab, close button) is dimmed, disabled, or blocked while generation is active.
8. In `LiveCursors`, a cursor whose presence has `thinking: true` shows a small spinner in its name badge; `thinking: false` or a missing field shows no spinner. (Only applies when that participant's cursor is otherwise rendered at all — see Open Questions #3.)
9. No new AI generation logic is added, no background task is triggered from this spec's code, and no new Liveblocks feed/mechanism is introduced beyond consuming the existing `ai-status-feed`/presence — matching this spec's own Scope Limits.
10. `npm run build` passes, along with this repo's standard gates (`npx tsc --noEmit`, `npx eslint .`, `npx vitest run`).

### Open questions

1. **`AiSidebar` currently renders outside the Liveblocks room boundary.** Reading `components/editor/workspace-shell.tsx` and `components/editor/canvas.tsx` directly: `LiveblocksProvider`/`RoomProvider` are both scoped *inside* `Canvas`, and `WorkspaceShell` renders `<Canvas>` and `<AiSidebar>` as plain siblings — `AiSidebar` has no ancestor `RoomProvider` today, so it cannot call `useEventListener`/`useOthers`/any other room hook directly. `LiveCursors`/`PresenceAvatars` don't have this problem because they're rendered by `CanvasFlow` itself, inside the boundary. Recommendation: do **not** restructure the provider tree (moving `RoomProvider` up to wrap both `Canvas` and `AiSidebar` would be a much larger, riskier change touching how the canvas's own Suspense/error-boundary fallback interacts with a sidebar that has nothing to do with canvas rendering). Instead, reuse the exact `onSaveStatusChange` pattern spec 21 already established for this identical category of problem: `CanvasFlow` (inside the boundary) subscribes and pushes the latest value up via a new `onAiStatusChange` callback to `WorkspaceShell`, which threads it down to `AiSidebar` as a plain prop. This is a recommendation, not a decision made unilaterally — flagging for the Senior Developer to confirm, since it's the one structurally significant call in this brief.
2. **Optional-`text` schema vs. spec 23's always-required `text`.** This spec's own text asks for an optional `text` field in the formalized schema, but spec 23's shipped `DesignAgentStatusMessage` (`lib/design-agent-room.ts`) always sends a required `text: string` — which trivially satisfies "optional" (a required field is a valid instance of an optional one), so no producer change is *required* for correctness. However, leaving two independently-typed, structurally-similar interfaces (`lib/design-agent-room.ts#DesignAgentStatusMessage` and `types/tasks.ts#AiStatusMessage`) risks them silently drifting apart later (e.g., spec 27/29's spec-generation task adding a new stage value in only one of the two). Recommendation: once `types/tasks.ts` exists, update `lib/design-agent-room.ts`'s `DesignAgentStatusStage`/`DesignAgentStatusMessage` to import and reuse the canonical `types/tasks.ts` types rather than keep a duplicate — a small, additive, import-only change (not a behavior change to the broadcast logic itself), consistent with `code-standards.md`'s "fix root causes — do not layer workarounds." Flagging as a recommendation since it technically touches a spec-23-owned file; the Senior Developer may reasonably decide the duplication is acceptable at this scale instead.
3. **The cursor "thinking" spinner will often have nothing to attach to.** Spec 23's own presence semantics (see its Dev Notes) set the AI's `cursor` to `null` for most of the `"start"`/early-`"processing"` window and only populate a real `{x, y}` once a node has actually been added or moved late in the run — meaning `LiveCursor`'s existing `other.cursor === null` early return will frequently hide the Ghost AI badge entirely during exactly the period this spec wants a spinner to be visible. Recommendation: implement this spec's requirement literally as written ("show a small spinner in their cursor name badge") — decorate the badge that already renders, don't invent a new floating "AI is thinking" indicator untethered to a cursor position, since that would be a different UI element this spec's text doesn't ask for. The sidebar status line (deliverable above) is the reliable, always-visible signal for "AI is working" regardless of cursor position; the cursor spinner is a secondary, best-effort visual that will sometimes just not appear. Not a blocker, but worth the Senior Developer/QA knowing this is expected behavior, not a bug, before filing it as one.
4. **Exact placement of the sidebar status line** isn't specified by the spec text beyond "in the sidebar." Recommendation: place it in the input-row area of `ai-architect-tab.tsx` (near the Textarea/Send button, similar visual weight to `SaveStatusIndicator`), so it doesn't compete with the scrollable message list or empty-state layout above it. A Dev-level layout call, not a product decision.
5. **Overlap with spec 26's own status-strip/spinner/disabled-input language.** `context/feature-specs/26-design-agent-frontend.md` independently redescribes very similar UI ("Show a compact status strip above the input only when a run is active," "While running: show spinner," "disable the chat input") as part of wiring the real submit flow. Read together, spec 26's phrasing reads as depending on spec 24 having already built this UI (spec 20's own text: "specs 22/24/25/26/27/29's job to wire on top of this shell... without redesigning it"), with spec 26 additionally gating the same signal off its own `useRealtimeRun`-sourced run state for the submitting client. Recommendation: build this spec's status line/disabling/spinner driven purely off `ai-status-feed` (room-wide, shared — matching "make the status visible to everyone in the room"), so spec 26 can layer its own submit-flow concerns on top without needing to redesign what this spec ships. Also note spec 26's UI Details mention a "green accent (`#62C073`)" for its own chat bubbles/submit button, which doesn't match `ui-context.md`'s already-established `--accent-ai`/`text-ai-text` (indigo-purple) styling this sidebar currently uses everywhere else (Bot icon, active tab, Send button, assistant bubbles) — that tension belongs to spec 26 to resolve, not this spec; this spec's own status line should stay consistent with the sidebar's existing `--accent-ai` token, not spec 26's new color.
