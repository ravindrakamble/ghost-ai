## Analyst Brief

### Scope statement

Wire the AI sidebar's existing chat input/Send button (spec 20) to actually trigger a design-agent run: on submit, push the prompt to the already-real `ai-chat` feed (spec 25), call `POST /api/ai/design` and `POST /api/ai/design/token` (spec 22) to obtain a `runId`/public token, track that specific run's live status client-side via `useRealtimeRun`, and — once it settles — push a final AI-authored (or error) message back onto `ai-chat`. This is the last piece of the AI-generation chain end to end from the sidebar's own UI; it does not touch backend/Trigger.dev logic (spec 22/23's territory, already delivered), does not fetch or manually apply the resulting graph (the canvas already reflects server-side Storage writes automatically via `useLiveblocksFlow`), and does not redesign the sidebar shell, tabs, or the room-wide status line spec 24 already built.

### Acceptance criteria

1. Submitting a prompt from the AI Architect tab's existing input/Send button first pushes the trimmed prompt onto `ai-chat` (via the existing spec-25 `sendMessage`, `role: "user"`), then calls `POST /api/ai/design` with `{ prompt, roomId, projectId }` (both room/project fields equal to the current project's ID) and receives a `runId` in response.
2. On receiving a `runId`, the client calls `POST /api/ai/design/token` with `{ runId }` to obtain a run-scoped public token, and stores both the `runId` and token in local component state.
3. `useRealtimeRun(runId, { accessToken: publicToken })`, from a genuinely installed `@trigger.dev/react-hooks` dependency, is used to track the triggered run's live status client-side.
4. While this client's own triggered run is in flight — from the moment of submission until `useRealtimeRun` reports a terminal state — the chat `Textarea` and Send button are disabled and the Send button shows a spinner, with no gap between submission and the room-wide `ai-status-feed`'s first broadcast.
5. The sidebar shows exactly one "AI is working" status indication during an active run — the existing spec-24 status line driven by the room-wide `ai-status-feed`, with no second/duplicate status-strip element introduced by this spec.
6. When `useRealtimeRun` reports this client's own triggered run completed successfully, a final AI-authored message (`role: "assistant"`) is pushed onto the shared `ai-chat` feed, and the local `runId`/token state is cleared.
7. When the run fails — either the initial `POST /api/ai/design`/`POST /api/ai/design/token` calls failing before a `runId`/subscription ever exists, or `useRealtimeRun` reporting a failed/errored terminal state — an error-describing message (`role: "assistant"`) is pushed onto `ai-chat`, and the local `runId`/token state is cleared the same way.
8. No manual node/edge mutation of any kind is added anywhere in this diff — the canvas continues to reflect AI-driven changes purely through the existing, unmodified `useLiveblocksFlow` subscription in `CanvasFlow`.
9. No `app/api/ai/*` route, `trigger/*` file, or `lib/design-agent-*` file is modified in this diff.
10. All new/changed UI in this diff uses only existing `ui-context.md` tokens (`--accent-ai`/`text-ai-text`/`bg-ai`, and the chat-bubble/status-line/error-indicator styling specs 20/24/25 already established) — no new hardcoded color (including the raw spec text's own mentioned green `#62C073`) appears anywhere in the diff.
11. `npm run build` passes, along with this repo's standard gates (`npx tsc --noEmit`, `npx eslint .`, `npx vitest run`).

### Open questions

1. **`@trigger.dev/react-hooks` is not an installed dependency.** Confirmed by reading `package.json`, `package-lock.json`, and `node_modules` directly — only `@trigger.dev/sdk` (a production dependency) and `@trigger.dev/build` (a dev dependency) exist anywhere in this repo; no `@trigger.dev/react-hooks` entry appears in any of the three. The raw spec text names `useRealtimeRun(runId, { accessToken: publicToken })` specifically, which is exported by `@trigger.dev/react-hooks`, not `@trigger.dev/sdk`. This is the same category of gap specs 22 (`@trigger.dev/sdk`), 23 (`@ai-sdk/google`/`ai`), and 25 (`zod`) each independently found and closed by installing the genuinely-needed package. Recommendation: install `@trigger.dev/react-hooks` (pinned to the same `4.5.12` version already used for `@trigger.dev/sdk`/`@trigger.dev/build`, per this repo's own version-pinning precedent from the Trigger.dev provisioning work) as a new production dependency, and — per this repo's established "read the installed SDK, not training data" precedent (specs 18/22/23/24/25) — verify `useRealtimeRun`'s real exported signature and its run-object shape (in particular, what `status` values count as "complete" vs. "failed") directly against the installed package's own type declarations once added, rather than assuming them. Flagging as a recommendation, not a unilateral decision, since it is a new production dependency.
2. **`POST /api/ai/design`'s real response shape doesn't match the raw spec text's "read `{ runId, publicToken }` from the response."** Reading `app/api/ai/design/route.ts` directly: it returns only `{ runId }`. The public token comes from a second, separate endpoint — `POST /api/ai/design/token`, given `{ runId }` in its body, returning `{ token }` — per spec 22's own already-delivered, already-tested design (a deliberate two-step split: the first call is gated by project-membership access, the second by `TaskRun.userId` ownership specifically, so another collaborator can't grab a token for someone else's run). Recommendation: implement the submit flow as two sequential `fetch` calls (`POST /api/ai/design` → `runId`, then `POST /api/ai/design/token` with that `runId` → `token`), storing the second call's `token` as the local `publicToken` state `useRealtimeRun`'s `accessToken` option expects. This is not a new design decision so much as correcting the raw spec text's premise against the already-shipped, already-tested API shape — the same category of correction spec 22's own Analyst Brief made for its request/response fields.
3. **Where `runId`/`publicToken` state should live, given the same provider-boundary constraint specs 24/25 hit.** Unlike `ai-status-feed`/`ai-chat` (both genuine Liveblocks room mechanisms, requiring a component inside `RoomProvider`), `useRealtimeRun` is a plain Trigger.dev React hook that takes its `accessToken` directly as an argument — it has no dependency on Liveblocks' `RoomProvider`/`LiveblocksProvider` context at all. Recommendation: own `runId`/`publicToken` directly in `AiArchitectTab` (which already sits outside the room boundary, per specs 24/25's own already-established constraint) via local `useState` — no callback-push-up/down through `CanvasFlow`/`Canvas`/`WorkspaceShell` is needed for this specific piece of state, unlike every other AI-related mechanism this sidebar consumes. This is the one genuinely different structural call in this brief relative to specs 24/25's precedent, flagged for the Senior Developer to confirm.
4. **Overlap between this spec's own "status strip" text and spec 24's already-built status line.** The raw spec text (`### 4. Status display`) independently describes "read the latest message from `ai-status-feed`... show a compact status strip above the input only when a run is active" — this is, functionally, exactly what spec 24 already shipped in `ai-architect-tab.tsx` (a status line + disabled input + spinner, gated on `aiStatus.stage` being `"start"`/`"processing"`). Spec 24's own Analyst Brief (Open Questions #5) already anticipated this overlap and deliberately built its status line off `ai-status-feed` alone, explicitly leaving room for "spec 26 to layer its own `useRealtimeRun`-sourced concerns on top without needing to redesign this UI." Recommendation: this spec should extend spec 24's existing status line/disabled/spinner condition (by OR-ing in the local "this client's own run hasn't reached a terminal state yet" signal — see Open Questions #6) rather than build a second, competing status-strip component. Not a blocker, but worth the Senior Developer/QA knowing this is the expected reading, not an oversight if no new status-strip component appears in the diff.
5. **What "push a final AI message to `ai-chat`" and "show errors as messages in `ai-chat` feed" concretely require, given today's `sendMessage` shape.** Reading `hooks/use-ai-chat-feed.ts` directly: the existing `sendMessage` function hardcodes `role: "user"` on every outgoing message (a deliberate choice, preserving spec 25's own acceptance criterion 7 — "every message rendered through this spec's own send path carries `role: 'user'`"). Nothing in the codebase today can produce a `role: "assistant"` message — `trigger/design-agent.ts` (server-side) writes only to `ai-status-feed`/canvas Storage/presence, never to the `ai-chat` Storage `LiveList`. Since this spec's own Scope Limits forbid backend/Trigger.dev changes, the AI-authored/error message has to be synthesized and pushed **client-side**, by whichever browser tab actually submitted the prompt, once its own `useRealtimeRun` subscription reports the run's outcome — the pushed message still lands in the shared Storage `LiveList`, so every other connected participant sees it too, satisfying "keep everything collaborative, all updates should be visible across clients" even though only the submitting client performs the write. Recommendation: add a new `sendAgentMessage` function to `hooks/use-ai-chat-feed.ts` (additive, alongside the untouched `sendMessage`) that hardcodes `role: "assistant"` and a fixed `sender` (recommend `"Ghost AI"`, reusing `lib/design-agent-room.ts#GHOST_AI_USER_NAME`'s already-established display name for the same conceptual actor), threaded down through the same callback-push-up/down pattern spec 25 established for `sendMessage` itself. An error message uses the same `sendAgentMessage` path (schema only supports `"user"`/`"assistant"` roles, no separate "system"/"error" role) with error-describing `content`. Flagging as a recommendation, not a unilateral decision, since it's new capability on a spec-25-owned file.
6. **The pre-broadcast timing gap between submission and `ai-status-feed`'s first message.** `aiStatus` (spec 24) only reflects whatever `trigger/design-agent.ts` has broadcast so far; there's a real window — the `POST /api/ai/design` round-trip, `POST /api/ai/design/token`, and however long it takes the triggered task to actually start running and call `broadcastDesignAgentStatus(..., { stage: "start" })` — during which `aiStatus` may still show `null` or a stale `"complete"`/`"error"` from a previous run, even though this client has genuinely just submitted a new one. Recommendation: gate the disabled/spinner condition on `isGenerating || Boolean(runId)` (i.e., also disabled whenever this client's own local `runId` state is non-null, regardless of what `aiStatus` currently says), closing the gap without touching spec 24's own `aiStatus`-driven logic. A Dev-level implementation detail within the spirit of both specs' text, not a literal requirement traceable to specific spec wording beyond "disable the chat input" while a run — from this client's own perspective — is active.
7. **The raw spec text's own color guidance conflicts with `ui-context.md`'s established tokens and this spec's own Scope Limits.** The spec's UI Details section asks for a green accent (`#62C073`) on chat bubbles/the submit button/status strip — but `ui-context.md`'s Theme table has no green UI-chrome token at all (`#62C073` only appears as one of the eight `NODE_COLORS` canvas-node-fill/text pairings, a completely different design-system layer with no bearing on sidebar chrome), and this spec's own Scope Limits explicitly say "do not hardcode a new theme outside existing tokens" — a direct, self-contradicting instruction within the spec's own text. Spec 24's Analyst Brief already flagged this exact tension (Open Questions #5) and recommended keeping the sidebar's existing `--accent-ai`/`text-ai-text` token pairing, which is what the currently-shipped Bot icon, active tab, Send button, and assistant chat bubbles all already use. Recommendation: this spec should not introduce green anywhere — reuse the existing `--accent-ai`/`text-ai-text`/`bg-ai` tokens and the chat-bubble styling spec 25 already built (`border-brand`/`bg-accent-dim` for user, `border-surface-border`/`bg-subtle`/`text-ai-text` for assistant) rather than adding a new color, consistent with both this spec's own literal Scope Limit and `code-standards.md`'s "no hardcoded hex values" rule.
8. **`useRealtimeRun`'s exact run-status vocabulary can't be pinned without reading the installed package.** Once `@trigger.dev/react-hooks` is actually installed (Open Questions #1), the Senior Developer should read its real type declarations directly (this repo's own established precedent, not assumption from training data) to determine the exact terminal-state status strings (e.g. whatever the equivalent of `"COMPLETED"` vs. `"FAILED"`/`"CRASHED"`/`"TIMED_OUT"`/`"CANCELED"` actually is in the installed version) that acceptance criteria 6/7 depend on, rather than guessing a plausible-sounding set.

This spec only extends the *disabled/spinner* condition (a separate concern from the status line's own visibility) with the new `isOwnRunInFlight` signal — no new visible status element was added anywhere in the diff.
5. **Open Questions #5 (`sendAgentMessage` design) — followed as recommended, with one naming deviation.** Added `sendAgentMessage` to `useAiChatFeed()`'s return, hardcoding `role: "assistant"` and a fixed sender. Used a fixed sender constant `"Ghost AI"` matching `lib/design-agent-room.ts#GHOST_AI_USER_NAME`'s literal value, but defined as an independent constant in `hooks/use-ai-chat-feed.ts` rather than importing that module directly — `lib/design-agent-room.ts` transitively imports `lib/liveblocks.ts`'s server-only Liveblocks client (reads `LIVEBLOCKS_SECRET_KEY`), which has no business being pulled into a `"use client"` hook's bundle. An error message uses the same `sendAgentMessage` path with error-describing content, exactly as recommended (the schema has no third "system"/"error" role).
6. **Open Questions #6 (closing the pre-broadcast timing gap) — implemented with an additional refinement beyond the brief's literal suggestion.** The brief recommended gating on `isGenerating || Boolean(runId)`, but re-reading acceptance criterion 4's "from the moment of submission" more literally, a `runId` alone doesn't exist yet during the two `POST` round-trips themselves — so a third local signal, `isSubmittingRun` (set synchronously at the very top of `submitDesignRequest`, before either `fetch` call), was added and OR-ed in alongside `Boolean(runId)`, closing that earlier sub-window too. This is a Dev-level extension within the spirit of the brief's own reasoning, not a deviation from it.
7. **A real bug the mechanical gate itself caught: `react-hooks/set-state-in-effect`.** The first draft's completion effect called `setRunId(null)`/`setPublicToken(null)` directly inside the `useEffect` reacting to `realtimeRun` — ESLint's `react-hooks/set-state-in-effect` rule (a real, non-`.trigger/tmp` finding) flagged this as a cascading-render risk. Investigated whether `useRealtimeRun`'s own `onComplete` callback option could sidestep the whole problem — read its real source and found `onComplete` only fires **once per mounted hook instance**, ever (its own internal `hasCalledOnCompleteRef` never resets across a new `runId`), which would silently break a second/third submission within the same sidebar session. Redesigned instead around a derived `isRunSettled` boolean (`realtimeRun.id === runId && realtimeRun.isCompleted`, computed at render time, not via effect-driven state) and a `handledRunIdRef` (a plain ref mutation, not a `setState` call) to guard against double-firing the message push. `runId`/`publicToken` are deliberately never reset back to `null` on completion anymore — `isRunSettled` alone already makes `isOwnRunInFlight`/`isBusy` correctly fall back to "not busy" without that reset, and the next submission's own success path overwrites both with fresh values regardless of what they held before. The pre-`runId`-ever-existing POST-failure path (inside `submitDesignRequest`'s own `catch`, not inside a `useEffect`) still resets both to `null`, since that's a normal event-handler-triggered `setState`, not an effect-body one.
8. **Open Questions #8 (`useRealtimeRun`'s real terminal-state vocabulary) — read directly, not guessed.** `@trigger.dev/core`'s `RunShape` type exposes ready-made `isCompleted`/`isSuccess`/`isFailed` booleans (derived server-side from the full `RunStatus` enum — `COMPLETED`/`CANCELED`/`FAILED`/`CRASHED`/`SYSTEM_FAILURE`/`EXPIRED`/`TIMED_OUT`, confirmed by reading `@trigger.dev/core/dist/esm/v3/schemas/api.js`), so this diff never needed to hand-roll its own terminal-status string matching — `realtimeRun.isCompleted`/`realtimeRun.isSuccess`/`realtimeRun.error?.message` are used directly.
9. **Deliberately not handling `useRealtimeRun`'s own top-level `error` return (distinct from `run.error`).** The hook also returns a subscription-level `error` (e.g. a network/auth failure fetching the run stream) separate from the run's own terminal-status fields. This was considered but dropped: `useRealtimeRun`'s internal SWR cache is keyed by a stable per-hook-call id (`useId()`), not by `runId`, so a *previous* run's stale `error` value could persist across a resubmission with no `runId` correlation to guard against it (unlike `run`, which at least carries its own `.id` field to compare against). Handling it correctly would need additional stale-tracking machinery for a failure mode (the token/subscription itself failing to connect, as opposed to the run failing) that's more of an infrastructure-level edge case than what acceptance criterion 7's "failed/errored terminal state" language most naturally describes. Flagged as a known limitation below rather than adding fragile, correlation-prone code for it.
