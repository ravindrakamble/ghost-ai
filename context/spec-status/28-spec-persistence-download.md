## Analyst Brief

### Scope statement

Add a `ProjectSpec` Prisma metadata model, persist a generated spec's Markdown content to Vercel Blob (following the same metadata-in-Postgres/content-in-Blob split `lib/canvas-blob.ts` already established for canvas snapshots), and add one authenticated, access-checked `GET` route that returns a persisted spec as a downloadable Markdown file. This is the backend persistence/download half spec 27 deliberately deferred — no frontend/UI logic, and no spec editor/viewer UI (that is spec 29's job, per `components/editor/specs-tab.tsx`'s own docblock and `context/feature-specs/29-spec-ui-integration.md`'s own text).

### Concrete deliverables

- `prisma/schema.prisma` (modified) — new `ProjectSpec` model per the raw spec text's own field list (`id`, `projectId` relation, `filePath`, `createdAt`), with a `@relation` to `Project` (`onDelete: Cascade`, mirroring `TaskRun`'s existing precedent) and a `specs ProjectSpec[]` back-relation added to `Project`. Requires a real migration against the provisioned Postgres database (same as spec 22's `TaskRun` addition). No `userId` field — access is derived from the project relationship via `getProjectAccess`, not per-spec ownership (the raw spec text's own field list has no `userId`, and nothing in the spec asks for one).
- `lib/spec-blob.ts` (new) — a Blob upload/fetch helper module mirroring `lib/canvas-blob.ts`'s exact shape (`requireBlobToken`, lazy per-call token check, no eager client instantiation so `next build`'s page-data collection stays safe): `uploadSpecMarkdown(projectId, specId, markdown)` writing to `specs/{projectId}/{specId}.md` (the exact pathname `architecture-context.md`'s Storage Model already names) and `fetchSpecMarkdown(blobUrl)` for the download route to read content server-side. **Must use `access: "private"`**, matching `lib/canvas-blob.ts`'s just-fixed, live-confirmed store configuration (a `"public"` `put`/`get` call is rejected outright by the provisioned store) — this is not optional or a fresh decision, it is the already-established, already-verified convention for this exact Blob store.
- The persistence step itself ("after a spec is generated: upload to Blob, store the path, link to the project") — concrete file TBD by the Senior Developer per Open Questions #1 below, but expected to live in either `trigger/generate-spec.ts` (modified) or a new dedicated route, not inline in the download route.
- `app/api/projects/[projectId]/specs/[specId]/download/route.ts` (new) — `GET`: `getProjectAccess(projectId)` (owner-or-collaborator, matching `app/api/projects/[projectId]/canvas/route.ts`'s existing gate rather than an owner-only one, since collaborators who can view/edit the canvas and trigger generation should also be able to download the result) → `prisma.projectSpec.findUnique({ where: { id: specId } })` → verify `spec.projectId === projectId` (404 if the spec exists but belongs to a different project — the raw spec text's own explicit "verify the spec belongs to that project" instruction) → `fetchSpecMarkdown(spec.filePath)` → return the Markdown as a downloadable attachment (`Content-Type: text/markdown; charset=utf-8`, `Content-Disposition: attachment; filename="..."` — exact filename convention is Open Questions #4) — never the raw Blob URL, mirroring the canvas `GET` route's "content only, never the URL" convention.
- Tests: `lib/spec-blob.test.ts` (new), the download route's own `route.test.ts` (new), and a test file for wherever the persistence step lands (new or extended, per Open Questions #1) — following this repo's established `vi.mock`/`vi.hoisted` conventions for Prisma, Clerk `auth()`, and the Blob/Trigger.dev SDK boundaries.
- No `components/*` file changes anywhere in this diff — the raw spec text's own explicit Scope Limit ("do not add frontend or UI logic"). `components/editor/specs-tab.tsx`'s inert "Generate Spec" button and static demo card stay exactly as spec 20 left them.
- No change to `lib/canvas-blob.ts`, `app/api/projects/[projectId]/canvas/route.ts`, or `hooks/use-canvas-autosave.ts` — the raw spec text's own explicit Scope Limit ("do not modify existing canvas persistence").

### Acceptance criteria

1. A `ProjectSpec` Prisma model exists with `id`, a `projectId` relation to `Project` (cascade-deleted with the project, matching `TaskRun`'s precedent), `filePath`, and `createdAt`. No spec Markdown content is stored as a Prisma column anywhere.
2. Once a spec's Markdown content is available, it is uploaded to Vercel Blob at `specs/{projectId}/{specId}.md` using `access: "private"`, and a `ProjectSpec` row is created (or updated) with the resulting Blob URL in `filePath`, linked to the correct `projectId`.
3. `GET /api/projects/[projectId]/specs/[specId]/download` returns 401 for an unauthenticated caller, and 404/403 (via `getProjectAccess(projectId)`) for a missing or non-member project, before any Prisma read or Blob fetch happens.
4. The same route returns 404 when `specId` does not exist, or exists but belongs to a different `projectId` than the one in the URL.
5. Given a valid authenticated owner-or-collaborator request and a real, existing spec belonging to that project, the route fetches the Markdown content from Blob server-side and returns it as a downloadable file (`Content-Type: text/markdown`, `Content-Disposition: attachment`) — never the raw Blob URL in the response body or headers.
6. A genuine upstream Blob failure (network/auth error, not "not found") surfaces as a 500, not a silently-empty or miscategorized 404 — mirroring `fetchCanvasSnapshot`'s existing distinction between "nothing there" and "a real failure happened."
7. No spec content is ever stored directly in Postgres — `ProjectSpec` holds only metadata (`filePath` + relations/timestamps), matching `code-standards.md`'s "Do not store large generated content directly in the database."
8. No Blob URL is ever exposed to an unauthenticated or non-member caller — every path to a spec's content goes through the access-checked download route.
9. `components/editor/specs-tab.tsx` and every other file under `components/` are unmodified anywhere in this diff.
10. `lib/canvas-blob.ts` and `app/api/projects/[projectId]/canvas/route.ts` are unmodified anywhere in this diff.
11. `npx tsc --noEmit`, `npx eslint .`, `npx vitest run`, and `npx next build` all pass, including a real Prisma migration for the new `ProjectSpec` model applied against the environment's provisioned database.

### Open questions

1. **Where does the persistence step (`ProjectSpec` create/update + Blob upload) actually live — inside `trigger/generate-spec.ts` itself, or a separate route?** The raw spec text's step 2 ("Save generated spec — After a spec is generated: upload…, store…, link…") describes what must happen but not what triggers it; unlike step 3 (the download route), it names no route path. Two real candidates: (a) modify `trigger/generate-spec.ts` so `runGenerateSpec` persists automatically right after `generateSpecMarkdown` succeeds, before the task returns; or (b) add a new, separate route (e.g. `POST /api/projects/[projectId]/specs`) that something — most plausibly spec 29's future frontend, reading the completed run's Markdown via `useRealtimeRun`'s output — calls afterward to persist it. **Recommendation: (a).** `architecture-context.md`'s own "Spec Generation" section already states the task's output is "Markdown technical spec **saved to the filesystem and linked to the project in the database**" — i.e., persistence is described as part of the task's own execution, not a separate client-triggered step. Prisma/Blob calls from inside a Trigger.dev task have no precedent yet in this codebase (`trigger/design-agent.ts` only touches Liveblocks, not Prisma), but nothing in `architecture-context.md`'s invariants restricts background tasks from writing to Postgres/Blob — Invariant 1 restricts *request handlers*, not background tasks. This also avoids inventing a new, spec-text-unnamed persistence route. Flagged clearly as the single largest interpretive gap in this spec's raw text — confirm before implementing, since it changes which file(s) are the primary deliverable.
2. **How is the Blob pathname's `specId` known before the `ProjectSpec` row exists?** `specs/{projectId}/{specId}.md` needs an ID, but Prisma's `@default(cuid())` only generates one at insert time. Recommendation: a two-write pattern — `prisma.projectSpec.create({ data: { projectId, filePath: "" } })` first (or a temporary placeholder value) to obtain the generated `id`, then `uploadSpecMarkdown(projectId, spec.id, markdown)`, then `prisma.projectSpec.update({ where: { id: spec.id }, data: { filePath: blobUrl } })`. This avoids adding a new ID-generation library dependency purely to precompute a cuid client-side. A Senior Developer who prefers a single-write approach (e.g., a library-generated ID passed explicitly as `id` on create) should confirm the tradeoff first — this is a small mechanical choice, not a product-behavior one.
3. **Whether this spec should also add a minimal `GET /api/projects/[projectId]/specs` list route**, even though the raw spec text's three numbered implementation items and "Check When Done" checklist name only the model, the save step, and the download route. **Recommendation: yes, add it**, for three converging reasons: (a) `project-overview.md`'s Features section states "Users can view and download generated specs" as part of Spec Generation — "view" implies a list is discoverable somewhere; (b) the download route's own "verify the spec belongs to that project" requirement presupposes a client already knows a real `specId`, which has to come from somewhere; (c) spec 29's raw text explicitly assumes "the existing ProjectSpec API" for fetching a list — without it, spec 29 is blocked on day one. This is flagged as a recommendation, not a hard requirement, because it genuinely goes beyond this spec's own literal checklist — if the Senior Developer disagrees and omits it, that should be called out explicitly in Dev Notes so the gap is visible to spec 29's own analyst pass rather than silently discovered mid-implementation. If added: metadata-only (`id`, `filePath` or a derived filename, `createdAt`), same `getProjectAccess(projectId)` gate, ordered by `createdAt desc`.
4. **Exact `Content-Disposition` filename convention.** Nothing in the raw spec text or `ui-context.md` pins one. Recommendation: `spec-{specId}.md` — stable, collision-free, no dependency on project name sanitization. A Senior Developer preference for a project-name-derived filename is a reasonable alternative but should be a documented choice, not left implicit.
5. **Whether multiple `ProjectSpec` rows per project are expected, or whether generation should overwrite a single record** (the way `Project.canvasJsonPath` holds exactly one snapshot). The raw spec text's own model has no unique constraint on `projectId`, and spec 29's raw text explicitly describes "a list of specs" (plural, each with its own `createdAt`) — not a single latest record. **Recommendation: allow multiple rows, one per generation run, no overwrite.** This is not the same as `project-overview.md`'s Out of Scope "versioned spec history and review workflows" — there is no version numbering, diffing, or review/approval flow here, just multiple independently generated artifacts a user can individually download, which the Features section's own "Specs are persisted as files and linked to the project" text already supports.
