## Analyst Brief

### Scope statement

Make the design agent's Gemini call return a short `summary` string alongside `actions`, thread that summary through `trigger/design-agent.ts` into `DesignAgentResult` and the "complete" `ai-status-feed` broadcast, surface it as the real `ai-chat` completion message in `components/editor/ai-architect-tab.tsx` instead of a hardcoded string, and add a "Critique this design" quick action that submits a fixed critique prompt through the existing `submitDesignRequest`/`POST /api/ai/design` pipeline unchanged. Nothing else — no new action kinds, no new API route, no critique-only/non-applying mode, no change to `trigger/generate-spec.ts` or the Specs tab.

### Concrete deliverables

- `lib/design-agent-ai.ts` (modified) — `DESIGN_AGENT_ACTIONS_JSON_SCHEMA` gains a required top-level `summary: { type: "string" }` alongside `actions`; `RawDesignAgentActionsResponse` gains `summary: string`; `isRawDesignAgentActionsResponse` validates it (non-empty string, matching the existing `isNonEmptyString` convention used for other required string fields like `addNode.label`); `interpretDesignPrompt`'s return type changes from `Promise<DesignAgentAction[]>` to `Promise<{ actions: DesignAgentAction[]; summary: string }>`; `buildPrompt` gains explicit instructions to (a) always produce a 1-2 sentence `summary` of what changed and why, grounded in `currentGraph`, and (b) when the request reads as a review/critique rather than a build request, actually critique the diagram (single points of failure, missing caching/queueing, unclear boundaries, etc.) before deciding on actions.
- `lib/design-agent-ai.test.ts` (modified) — existing mocked Gemini responses need a `summary` field added to stay schema-valid; new tests for: `summary` missing/empty/non-string rejected by `isRawDesignAgentActionsResponse` (and therefore surfaced as a `generateObject` validation failure, per the existing `jsonSchema()`/`validate` wiring), `interpretDesignPrompt` returning `{ actions, summary }` together, and the prompt text including the summary instruction.

- `components/editor/ai-architect-tab.tsx` (modified) — the run-completion `useEffect`'s success branch reads `realtimeRun.output?.summary` and pushes that via `pushAgentMessage` when it is a non-empty string, falling back to the existing `DESIGN_AGENT_SUCCESS_MESSAGE` only when it is missing/empty; a new "Critique this design" quick action with fixed prompt text, wired through the same `submitDesignRequest` path `handleSubmit` already uses for typed prompts (see Open Questions #2 for exact click behavior and placement).

### Acceptance criteria

1. `DESIGN_AGENT_ACTIONS_JSON_SCHEMA` requires `summary` (a string) as a top-level sibling of `actions`; a Gemini response missing or with an empty/non-string `summary` fails validation the same way an invalid action currently does (surfaces as a `generateObject` failure, not silently accepted).
2. `interpretDesignPrompt` returns `{ actions: DesignAgentAction[]; summary: string }` — callers no longer receive a bare array.
3. `buildPrompt`'s prompt text explicitly asks the model for a 1-2 sentence summary of what changed and why, grounded in the current graph, and explicitly instructs it to critique the diagram (SPOFs, missing caching/queueing, unclear boundaries) before choosing actions when the request reads as a review/critique rather than a build request.
4. `runDesignAgent` keeps the real `summary` from `interpretDesignPrompt` and returns it as part of `DesignAgentResult` (`{ roomId, actionCount, summary }`).
5. The `"complete"`-stage `ai-status-feed` broadcast's `text` is the real `summary` string, not the previous generic `"Ghost AI made N change(s)..."` text.
6. On a design-agent run completing successfully, the `ai-chat` completion message pushed by `ai-architect-tab.tsx` is the real `summary` from `realtimeRun.output?.summary` when it is a non-empty string.
7. If `realtimeRun.output?.summary` is missing, empty, or not a string, the completion message falls back to the existing generic `DESIGN_AGENT_SUCCESS_MESSAGE` — the run must never push an empty or malformed chat message.
8. The failure-path completion message (`buildDesignAgentFailureMessage`) is unchanged — this spec only touches the success branch's message content.
9. A "Critique this design" quick action is visible in the AI Architect tab and, when used, submits a fixed critique prompt through the exact same `submitDesignRequest`/`POST /api/ai/design` → token → `useRealtimeRun` pipeline already used for typed prompts — no new API route, no new request shape.
10. No new action kind is added to `DESIGN_AGENT_ACTION_KINDS`/`DesignAgentAction` — the critique flow reuses the existing 7 kinds and the existing action-application pipeline (`applyDesignAgentActions`) exactly as-is.
11. `trigger/generate-spec.ts`, `lib/generate-spec-ai.ts`, and `components/editor/specs-tab.tsx` are untouched.
12. No new AI provider/abstraction is introduced — the existing Gemini `generateObject` + `jsonSchema()` call in `lib/design-agent-ai.ts` is extended in place, not replaced or wrapped.
13. `npx tsc --noEmit`, `npx eslint` (scoped to changed files, consistent with prior specs' mechanical gate), `npx vitest run`, and `npx next build` all pass.

### Open questions

1. **How should `run.output` be typed so `realtimeRun.output?.summary` is real `DesignAgentResult`-typed access rather than `any`/`unknown`?** The raw spec text says "typed via `DesignAgentResult`" but doesn't specify the mechanism. `ai-architect-tab.tsx` currently calls `useRealtimeRun(runId ?? undefined, {...})` with no generic type parameter (spec 26's diff never needed `.output`), and `@trigger.dev/react-hooks`' own documented pattern for a typed `run.output` is `useRealtimeRun<typeof someTask>(...)`, which needs `typeof designAgentTask` in scope.
   **Recommendation:** `import type { designAgentTask, DesignAgentResult } from "@/trigger/design-agent"` (type-only — erased at build, does not bundle `@trigger.dev/sdk`/server task code into the client bundle) and call `useRealtimeRun<typeof designAgentTask>(...)`, which types `realtimeRun.output` as `DesignAgentResult | undefined` per the library's own generic. This mirrors `specs-tab.tsx`'s existing precedent of type-only-importing narrow types from a non-`components/` module (`import type { GenerateSpecGraphEdge, GenerateSpecGraphNode } from "@/lib/generate-spec-ai"`) — the only difference here is the source module is under `trigger/` rather than `lib/`, which `code-standards.md`'s `TypeScript`/`avoid any` rule and `architecture-context.md`'s system-boundaries section don't forbid at the type-only level (the boundary is about where *logic* lives, not where a type name is imported from). If the Senior Developer judges a type-only cross-boundary import undesirable, an acceptable alternative is re-exporting `DesignAgentResult` from a neutral location (e.g. `types/tasks.ts`) — either satisfies acceptance criterion 6/7 as long as `.output` access is genuinely typed, not `any`.

2. **Exact click behavior and placement of the "Critique this design" quick action.** The raw spec text says to add it "alongside the existing `STARTER_PROMPTS` chips" — which today render *only* in the empty-chat-history state (`chatMessages.length === 0`, per `ai-context.md`'s "AI Architect tab" section and the component's own conditional) and, on click, only *fill* the textarea rather than auto-submitting (documented explicitly in `ui-context.md`: "clicking a chip fills the textarea with its own text rather than auto-submitting"). Taken completely literally, "alongside the existing chips" would place the new action in that same empty-state-only block with the same fill-only behavior — but the raw spec's own scope line calls this a "one-click way to ask it to critique the existing diagram," and it says the action itself "submits" (not "fills") through `submitDesignRequest`. A critique action that only appears before any message has ever been sent, and that still requires a second manual Send click, satisfies neither the "one-click" framing nor the practical use case (a user typically wants to critique a diagram *after* generating/editing it, by which point `chatMessages` is no longer empty and the empty-state chip block is permanently gone for that room session).
   **Recommendation:** two independent sub-decisions, both flagged rather than decided unilaterally:
   (a) **Auto-submit vs. fill-only** — recommend auto-submit (call `sendMessage` + `submitDesignRequest` directly on click, mirroring `handleSubmit`'s body with the fixed critique prompt), since "one-click" and "submits" are fairly direct textual signals, and this is explicitly a different, second kind of control ("quick action") from the three "starter prompt chips" whose fill-only behavior was a deliberate, documented choice for a different purpose (letting a user edit a starting point before running it) not obviously meant to extend to this one.
   (b) **Visibility** — recommend rendering the critique quick action outside the `chatMessages.length === 0` gate (e.g., always present near the input row, or shown whenever it isn't the empty state instead of when it is) so it stays reachable once a diagram/conversation exists, since a `chatMessages.length === 0` gate would make it usable almost never in the room's real lifecycle. This is the one place this brief deviates from the raw spec text's literal collocation instruction, on the grounds that the literal reading actively defeats the stated purpose — Senior Developer should treat this as the analyst's best-supported reading, not a already-settled decision, and record whichever way it's resolved in Dev Notes.
   Whichever way (a)/(b) land, they must still route through the unmodified `submitDesignRequest`/`POST /api/ai/design` pipeline per acceptance criterion 9 — only the trigger point and visibility differ, not the request mechanism.

3. **Exact critique prompt text.** The raw spec says "fixed prompt text asking the agent to review the current diagram for architectural issues and apply improvements" but does not give the literal string.
   **Recommendation:** something close to `"Critique this design — review the current diagram for architectural issues (single points of failure, missing caching or queueing, unclear boundaries) and apply improvements."` A Dev-level copywriting choice within the spec's own description, not a literal requirement — any wording that (a) reads as a review/critique request so `buildPrompt`'s new critique-mode instruction actually triggers, and (b) explicitly asks for improvements to be applied (not just described), satisfies the spec.

4. **Does an empty-window edge case need a defensive fallback inside `runDesignAgent` itself for the `"complete"` broadcast, separate from `ai-architect-tab.tsx`'s fallback?** The raw spec only describes a fallback on the frontend ("fall back to the existing generic message only if missing"), and `runDesignAgent` only reaches its `"complete"` broadcast after `interpretDesignPrompt` has already resolved successfully — meaning `summary` is guaranteed non-empty *if* `isRawDesignAgentActionsResponse`'s new validation (acceptance criterion 1) enforces non-emptiness, since a schema-invalid response would have already made `generateObject` reject and thrown before `runDesignAgent` ever reaches the broadcast line.
   **Recommendation:** no separate fallback needed inside `runDesignAgent` — validate `summary` as a required non-empty string at the `isRawDesignAgentActionsResponse` boundary (acceptance criterion 1), which makes a non-empty `summary` an invariant by the time `runDesignAgent` uses it, consistent with this codebase's existing "validate at the boundary, trust it after" convention (`code-standards.md`'s "Validate unknown external input at system boundaries before trusting it").
